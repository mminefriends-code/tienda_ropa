## CU28 — Realizar Reserva de Múltiples Prendas

CASO DE USO | CU28 - Realizar Reserva de Múltiples Prendas
--- | ---
PROPÓSITO | Permitir al Cliente reservar varias prendas (cada una con su talla, color y cantidad) para probarlas luego en la sucursal física que elija, validando la disponibilidad real del inventario al momento de la reserva y dejando la solicitud en estado 'Solicitada' para su preparación por el Encargado de Sucursal (CU30).
DESCRIPCIÓN | Desde el módulo "Reservas → Nueva Reserva" (/reservas/nueva en React, ClienteLayout), el Cliente revisa el catálogo (CU16) y va agregando prendas; por cada una elige talla y color —que en conjunto determinan el id_ptc en producto_talla_color— y una cantidad. El panel lateral "Tu reserva" acumula los ítems y muestra el total. El formulario solicita la sucursal de retiro (sucursales con estado 'Activo'), la fecha de visita (fecha_reserva) y la hora (hora_reserva), que debe caer dentro del horario de atención de esa sucursal definido en sucursal_horarios (dia_semana + horario_apertura/horario_cierre). Al presionar "Confirmar Reserva", el frontend envía POST /api/v1/reservas con Authorization: Bearer {access_token} y body { "id_sucursal": number, "fecha_reserva": "YYYY-MM-DD", "hora_reserva": "HH:MM:SS", "items": [ { "id_ptc": number, "cantidad": number } ] }. El backend NestJS ReservasService.crear(): (a) valida el token y el permiso gestionar_reservas en roles.permisos_json; (b) valida que exista clientes.id_cliente (vía clientes.usuario_id = usuarios.id), que la sucursal esté Activa, que la fecha no sea pasada y que la hora esté dentro del horario; (c) por cada ítem valida el id_ptc y que inventario_stock.cantidad_disponible >= cantidad para la pareja (id_ptc, id_sucursal); (d) inserta en reservas { id_cliente, id_usuario, id_sucursal, fecha_reserva, hora_reserva, estado: 'Solicitada', fecha_creacion: NOW() } con RETURNING id_reserva; (e) inserta los reserva_items obtenidos; (f) actualiza inventario_stock: cantidad_reservada = cantidad_reservada + cantidad y cantidad_disponible = cantidad_disponible - cantidad; (g) inserta en movimientos_inventario { id_ptc, id_sucursal, tipo_movimiento: 'Reserva', cantidad: -cantidad, stock_anterior, stock_posterior, id_reserva, id_usuario, fecha: NOW() }; (h) registra en bitacora_auditoria { accion_sql: 'INSERT', tabla_afectada: 'reservas', id_registro: id_reserva, new_data: { sucursal, fecha, hora, items } } con IP y user agent del request; (i) retorna HTTP 201 con { id_reserva, estado, sucursal, fecha, hora, items }. El frontend muestra el toast "Reserva confirmada con código #X. Te esperamos en [sucursal] el [fecha] a las [hora]." y un botón "Ver Mis Reservas" que navega a CU29.
ACTORES | Cliente (permiso gestionar_reservas). Encargado de Sucursal y Administrador solo para seguimiento y preparación (CU29/CU30). Cualquier otro rol: sin acceso (403).
ACTOR INICIADOR | Cliente registrado en la plataforma que desea asegurar varias prendas para probarlas en una sucursal física.
PRECONDICIÓN | - El Cliente tiene sesión activa con JWT válido y rol Cliente cuyo permisos_json incluye gestionar_reservas (leído desde la DB en cada request por RolesService.cargarPermisos, con soporte de comodín "*"). - Existe el registro en clientes (clientes.id_cliente) vinculado a usuarios.id mediante clientes.usuario_id. - Las tablas reservas, reserva_items, inventario_stock, movimientos_inventario, producto_talla_color, productos, tallas, colores, sucursales y sucursal_horarios existen en el esquema. - La sucursal seleccionada tiene estado 'Activo' y horario definido en sucursal_horarios para el día elegido. - Cada id_ptc seleccionado existe y su inventario_stock de la sucursal tiene cantidad_disponible >= cantidad solicitada.
FLUJO PRINCIPAL (Camino Feliz) | 1. El Cliente inicia sesión (CU01) e ingresa a la tienda. 2. Abre el catálogo (CU16) y en una prenda pulsa "Reservar para probar". 3. Selecciona talla, color y cantidad; el ítem se agrega al panel "Tu reserva". 4. Repite el paso 3 con varias prendas; puede quitar o cambiar cantidades. 5. Pulsa "Continuar"; el formulario pide sucursal, fecha y hora. 6. Selecciona la sucursal donde quiere probar y el sistema carga sus horarios; elige fecha y hora dentro del horario. 7. Pulsa "Confirmar Reserva"; el frontend valida los campos y envía POST /api/v1/reservas. 8. El backend valida los ítems y el stock; inserta la reserva 'Solicitada' y sus ítems; actualiza el inventario (reservado +, disponible -) y registra el movimiento de Kardex tipo 'Reserva'. 9. Retorna 201 y el frontend muestra el código y los datos de la reserva. 10. La reserva queda visible en "Mis Reservas" (CU29) y se notifica a la sucursal (CU30).
POST CONDICIÓN | La reserva quedó creada con estado 'Solicitada' y su detalle en reserva_items. El inventario de la sucursal quedó actualizado (cantidad_reservada incrementada y cantidad_disponible decrementada) y se registró el movimiento de Kardex tipo 'Reserva' trazable al id_reserva. La reserva es visible para el Cliente (CU29) y para el Encargado (CU30/CU31). La bitácora de auditoría registra la creación con old_data/new_data, IP y user agent.
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos. Sesión sin gestionar_reservas → HTTP 403 { message: "No tienes permisos para realizar reservas." }; el módulo no aparece en el menú del Cliente y el acceso por URL directa muestra la pantalla "Acceso denegado" mientras el backend responde 403. - E2: Sesión expirada/inválida → HTTP 401; AuthContext limpia sesión y redirige a /login. - E3: Sin ítems. items vacío o nulo → HTTP 422 { message: "Debes seleccionar al menos una prenda." }. - E4: Ítem inválido. id_ptc inexistente → 422 { message: "Prenda no encontrada." }; cantidad <= 0 → 422 { message: "La cantidad debe ser mayor a cero." }; prenda cuyo estado_stock = 'Sin stock' o producto inactivo → 409 { message: "La prenda [nombre] no está disponible actualmente." }. - E5: Stock insuficiente. Para algún ítem cantidad > cantidad_disponible → HTTP 409 { message: "Stock insuficiente de la prenda [nombre] (talla, color). Disponible: X." }; la transacción se revierte completa (rollback) para no crear reservas parciales. - E6: Sucursal/fecha/hora inválidas. Sucursal inactiva → 422 { message: "La sucursal seleccionada no está disponible para reservas." }; fecha anterior a hoy → 422 { message: "La fecha de la reserva no puede ser anterior a hoy." }; hora fuera del horario → 422 { message: "La hora seleccionada está fuera del horario de atención de la sucursal." }. - E7: Error de red/servidor. Backend sin respuesta → mensaje "Error de conexión. Verifica tu acceso a internet e intenta de nuevo." sin dejar la reserva a medias. - E8: Doble envío del formulario. El botón "Confirmar Reserva" queda en loading (deshabilitado) mientras se procesa para evitar reservas duplicadas.

## CU29 — Consultar y Cancelar el Estado de una Reserva

CASO DE USO | CU29 - Consultar y Cancelar el Estado de una Reserva
--- | ---
PROPÓSITO | Permitir al Cliente consultar en tiempo real el estado de sus reservas ('Solicitada', 'Preparada', 'En tienda', 'Cumplida' o 'Cancelada') junto con el detalle de prendas, y cancelar aquellas que aún no han sido atendidas, liberando el stock reservado y registrando el cambio en la bitácora.
DESCRIPCIÓN | Desde el módulo "Mis Reservas" (/reservas en React, ClienteLayout), el Cliente ve la lista de sus reservas ordenadas de la más reciente a la más antigua; cada tarjeta muestra el código id_reserva, sucursal, fecha y hora de atención (fecha_reserva, hora_reserva), cantidad de prendas y un badge con el estado (Solicitada: brand, Preparada: warning, En tienda: accent, Cumplida: success, Cancelada: danger). Al pulsar una reserva se abre el detalle con los reserva_items (prenda desde productos.nombre, talla desde tallas.nombre, color desde colores.nombre y cantidad), la sucursal, la fecha/hora y la línea de tiempo fecha_creacion → fecha_preparada → fecha_atendida con el id_encargado. El frontend consulta GET /api/v1/reservas/mias (lista del Cliente autenticado) y GET /api/v1/reservas/:id (detalle). Para cancelar, el Cliente pulsa "Cancelar Reserva", confirma en el diálogo "¿Estás seguro? Se liberará el stock de las prendas reservadas." y el frontend envía PATCH /api/v1/reservas/:id/cancelar con Authorization: Bearer {access_token}. El backend NestJS ReservasService.cancelar(): (a) valida el token y el permiso gestionar_reservas; (b) valida que la reserva exista y pertenezca al Cliente autenticado (reservas.id_cliente = clientes.id_cliente del usuario) y que su estado sea 'Solicitada' o 'Preparada'; (c) actualiza reservas.estado = 'Cancelada'; (d) por cada reserva_item repone el inventario en inventario_stock: cantidad_reservada = cantidad_reservada - cantidad y cantidad_disponible = cantidad_disponible + cantidad; (e) inserta en movimientos_inventario un movimiento inverso con tipo_movimiento = 'Reserva', cantidad positiva, stock_anterior/stock_posterior e id_reserva, con referencia de la cancelación; (f) inserta en bitacora_auditoria { accion_sql: 'UPDATE', tabla_afectada: 'reservas', id_registro, old_data: { estado: 'Solicitada'/'Preparada' }, new_data: { estado: 'Cancelada' } } con IP y user agent; (g) retorna HTTP 200 con { message: "Reserva cancelada correctamente.", estado: 'Cancelada' }. El frontend actualiza el badge a Cancelada y muestra el toast de éxito.
ACTORES | Cliente (permiso gestionar_reservas) para consultar y cancelar sus propias reservas. Encargado de Sucursal (gestionar_reservas) consulta las reservas de su sucursal pero no cancela por el Cliente (el proceso de atención lo definen CU30/CU31). Administrador con acceso de consulta (permiso "*"). Cualquier otro rol: sin acceso (403).
ACTOR INICIADOR | Cliente registrado que desea conocer el estado de sus reservas o liberar prendas que ya no podrá atender.
PRECONDICIÓN | - El Cliente tiene sesión activa con JWT válido y permiso gestionar_reservas en roles.permisos_json (leído de la DB en cada request, con soporte de comodín "*"). - Existe clientes.id_cliente vinculado a usuarios.id mediante clientes.usuario_id. - Las tablas reservas, reserva_items, producto_talla_color, productos, tallas, colores, sucursales, inventario_stock y movimientos_inventario existen en el esquema. - La reserva a consultar/cancelar pertenece al Cliente autenticado (reservas.id_cliente = clientes.id_cliente).
FLUJO PRINCIPAL (Camino Feliz) | 1. El Cliente inicia sesión (CU01) e ingresa a "Mis Reservas". 2. El frontend envía GET /api/v1/reservas/mias y muestra la lista con el badge de estado de cada reserva. 3. El Cliente abre una reserva; el frontend envía GET /api/v1/reservas/:id y carga el detalle con las prendas y la línea de tiempo. 4. Si el estado es 'Solicitada' o 'Preparada', el Cliente pulsa "Cancelar Reserva". 5. Confirma en el diálogo de advertencia. 6. El frontend envía PATCH /api/v1/reservas/:id/cancelar. 7. El backend valida que la reserva exista, sea del Cliente y esté en estado cancelable. 8. Actualiza reservas.estado = 'Cancelada'. 9. Repone el stock por cada ítem (cantidad_reservada - y cantidad_disponible +) y registra el movimiento de Kardex inverso. 10. Inserta la bitácora UPDATE con old_data/new_data. 11. Retorna HTTP 200 y el frontend actualiza el badge a Cancelada con toast de éxito.
POST CONDICIÓN | La reserva quedó en estado 'Cancelada' (ya no puede reactivarse ni generar devolución). El stock de la sucursal quedó liberado: cantidad_reservada decrementada y cantidad_disponible incrementada por cada ítem, con sus movimientos de Kardex y la bitácora de auditoría registrados con old_data/new_data.
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos. Sesión sin gestionar_reservas → HTTP 403 { message: "No tienes permisos para consultar reservas." }; el módulo no aparece en el menú y el acceso por URL directa muestra "Acceso denegado". - E2: Sesión expirada/inválida → HTTP 401; AuthContext limpia sesión y redirige a /login. - E3: Reserva no encontrada o ajena. id_reserva inexistente o que no pertenece al Cliente → HTTP 404 { message: "Reserva no encontrada." } sin revelar que existe (previene enumeración de reservas). - E4: Cancelación no permitida. Estado 'En tienda' o 'Cumplida' → HTTP 409 { message: "La reserva ya fue atendida y no puede cancelarse. Si tienes un inconveniente, contacta a la sucursal." }; estado 'Cancelada' → HTTP 409 { message: "La reserva ya no está vigente." }. - E5: Error de red/servidor. Backend sin respuesta → "Error de conexión. Verifica tu acceso a internet e intenta de nuevo." - E6: Doble envío del formulario. El botón "Cancelar Reserva" queda en loading (deshabilitado) mientras se procesa para evitar cancelaciones duplicadas.

## CU30 — Notificar Reserva a la Sucursal

CASO DE USO | CU30 - Notificar Reserva a la Sucursal
--- | ---
PROPÓSITO | Garantizar que la sucursal elegida por el Cliente sea notificada de cada nueva reserva 'Solicitada', para que el Encargado pueda visualizarla, preparar las prendas y atender al cliente, cerrando el ciclo iniciado en CU28.
DESCRIPCIÓN | Este caso se dispara automáticamente como postcondición de CU28 (al confirmarse una reserva): el backend NestJS termina de crear la reserva y la deja visible en el módulo "Reservas → Reservas de mi Sucursal" (/admin/reservas en React, EncargadoLayout y AdminLayout), que lista las reservas de la sucursal del Encargado (reservas.id_sucursal = usuarios_empleados.sucursal_id del usuario autenticado) con estado 'Solicitada' o 'Preparada'. El ítem "Reservas" del menú lateral muestra un badge con el conteo de reservas pendientes (estado 'Solicitada') que se refresca con polling cada 30 s. El Encargado puede pulsar "Ver" sobre una reserva para consultar su detalle completo (CU29) y prepararla (CU31). La notificación queda trazada en bitacora_auditoria con accion_sql = 'NOTIFICAR', tabla_afectada = 'reservas', id_registro = id_reserva y new_data = { sucursal, evento: 'Reserva nueva' } con IP y user agent del request; cuando la reserva pasa a 'Preparada' o 'En tienda', o se cancela, el contador de pendientes se decrementa. De forma opcional, si el servidor tiene configurado un servicio SMTP en el entorno (SMTP_HOST/SMTP_USER/SMTP_PASS), el backend envía un correo a la sucursal con el resumen de la reserva; si el correo falla, no se bloquea la operación y el error queda registrado en los logs del servidor.
ACTORES | Encargado de Sucursal (permiso gestionar_reservas, rol 'Encargado de Sucursal') como receptor y responsable de la atención. Administrador General (permiso "*") con supervisión global. Sistema (backend) como iniciador de la notificación. Cliente (CU28) como origen del evento.
ACTOR INICIADOR | El sistema (backend) al confirmarse la creación de una nueva reserva en CU28; el Encargado interactúa como receptor de la notificación.
PRECONDICIÓN | - El Encargado tiene sesión activa con JWT válido y permiso gestionar_reservas en roles.permisos_json. - El usuario autenticado tiene un registro en usuarios_empleados con sucursal_id correspondiente a su sucursal (para el Encargado) o permiso "*" (Administrador). - Existe la tabla reservas con el registro creado por CU28 en estado 'Solicitada' y su sucursal definida en reservas.id_sucursal. - Las tablas usuarios_empleados, sucursales, reserva_items e inventario_stock existen en el esquema.
FLUJO PRINCIPAL (Camino Feliz) | 1. El Cliente confirma la reserva en CU28 y el backend la registra en estado 'Solicitada' con su id_sucursal. 2. El backend identifica la sucursal y deja la reserva disponible para el Encargado de esa sucursal. 3. El ítem "Reservas" del menú lateral del Encargado queda con badge (N + 1) pendientes. 4. El Encargado inicia sesión (CU01) y abre "Reservas de mi Sucursal"; el frontend envía GET /api/v1/reservas/sucursal con Authorization: Bearer {access_token} y lista las reservas pendientes ordenadas por fecha_creacion DESC, mostrando código, prendas (resumen desde reserva_items/producto_talla_color/productos), cliente, fecha y hora de atención y badge 'Solicitada'. 5. El badge del menú se refresca con el polling de 30 s mientras haya pendientes. 6. El Encargado pulsa "Ver" para consultar el detalle (CU29) y luego preparar las prendas (CU31); al cambiar el estado a 'Preparada', el contador de pendientes baja. 7. Si un Cliente cancela (CU29), la reserva pasa a 'Cancelada' y también desaparece del pendiente. 8. (Opcional) Si hay SMTP configurado, el backend envía el correo de aviso a la sucursal con el resumen; si falla, registra el error solo en logs. La notificación queda trazada en la bitácora.
POST CONDICIÓN | La sucursal quedó notificada de la reserva: el Encargado la ve en su módulo con badge de pendientes y puede iniciar la preparación (CU31). El contador de pendientes refleja en tiempo real las reservas 'Solicitada' de la sucursal. El evento quedó registrado en la bitácora de auditoría con la trazabilidad de consulta.
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos. Sesión sin gestionar_reservas → HTTP 403 { message: "No tienes permisos para gestionar reservas." }; el módulo no aparece en el menú y el acceso por URL directa muestra "Acceso denegado". - E2: Sesión expirada/inválida → HTTP 401; AuthContext redirige a /login. - E3: Sucursal sin Encargado asignado. Si no existe usuarios_empleados con sucursal_id = reservas.id_sucursal y rol Encargado, la reserva queda 'Solicitada' sin badge para ningún usuario; el Administrador la puede ver en su listado global y el backend registra el estado en los logs para su asignación posterior (no se pierde la reserva). - E4: Fallo de correo (opcional). Si SMTP falla al enviar el aviso → se registra el error en api-server.err.log y se continúa: la notificación interna (listado + badge) siempre funciona y es la vía oficial. - E5: Error de red en el polling. Si la petición de refresco del badge falla, el frontend conserva el último conteo y reintenta en el siguiente ciclo sin bloquear la interfaz. - E6: Reserva cancelada antes de atender (CU29). La notificación se desactiva automáticamente y el badge baja; no es necesario eliminar el registro histórico.

## CU31 — Confirmar Recepción del Cliente en el Vestidor Físico

CASO DE USO | CU31 - Confirmar Recepción del Cliente en el Vestidor Físico
--- | ---
PROPÓSITO | Permitir al Encargado de Sucursal gestionar la atención presencial de una reserva: preparar las prendas reservadas, confirmar la llegada del Cliente al vestidor físico y cerrar la atención cuando la prueba finaliza, trasladando el estado por 'Preparada' → 'En tienda' → 'Cumplida' con trazabilidad completa.
DESCRIPCIÓN | Desde el módulo "Reservas → Reservas de mi Sucursal" (/admin/reservas en React, EncargadoLayout), el Encargado ve las reservas pendientes de su sucursal (reservas.id_sucursal = usuarios_empleados.sucursal_id). Sobre una reserva 'Solicitada' pulsa "Preparar Prendas": el frontend envía PATCH /api/v1/reservas/:id/preparar y el backend valida la pertenencia a la sucursal y el estado, actualiza reservas.estado = 'Preparada', reservas.id_encargado = usuario.id y reservas.fecha_preparada = NOW(), e inserta en bitacora_auditoria { accion_sql: 'UPDATE', tabla_afectada: 'reservas', old_data: { estado: 'Solicitada' }, new_data: { estado: 'Preparada', id_encargado } }. Cuando el Cliente llega al vestidor, el Encargado pulsa "Confirmar Recepción": PATCH /api/v1/reservas/:id/confirmar-recepcion, que valida estado 'Preparada', actualiza estado = 'En tienda' y fecha_atendida = NOW() y registra la bitácora. Al terminar la prueba el Encargado pulsa "Finalizar Atención": PATCH /api/v1/reservas/:id/finalizar, que valida estado 'En tienda' y actualiza estado = 'Cumplida'; si el Cliente no compró ninguna prenda (store no hubo venta vinculada), el backend libera el stock reservado por cada reserva_item (inventario_stock: cantidad_reservada = cantidad_reservada - cantidad y cantidad_disponible = cantidad_disponible + cantidad) e inserta movimientos_inventario tipo 'Reserva' inversos con id_reserva; si el Cliente compró, la venta (CU36/CU39) ya liberó el stock como venta y la reserva solo se marca 'Cumplida'. El badge de pendientes (estado 'Solicitada'/'Preparada') del menú baja al avanzar. Cada transición se valida contra la precondición exigida y se registra en bitácora con old_data/new_data, IP y user agent.
ACTORES | Encargado de Sucursal (permiso gestionar_reservas) como responsable de preparar y atender en el vestidor. Administrador General (permiso "*") con supervisión. El Cliente (CU28/CU29) está presente en la sucursal y es beneficiario de la atención.
ACTOR INICIADOR | Encargado de Sucursal que prepara las prendas y confirma la recepción del Cliente cuando este acude al vestidor físico.
PRECONDICIÓN | - El Encargado tiene sesión activa con JWT válido y permiso gestionar_reservas en roles.permisos_json. - El usuario autenticado tiene usuarios_empleados.sucursal_id igual al de la reserva (o permiso "*" para Administrador). - La reserva existe y pertenece a la sucursal; su estado es 'Solicitada' para preparar, 'Preparada' para confirmar recepción y 'En tienda' para finalizar. - Existen las tablas reservas, reserva_items, inventario_stock, movimientos_inventario, productos y producto_talla_color.
FLUJO PRINCIPAL (Camino Feliz) | 1. El Encargado inicia sesión (CU01) y abre "Reservas de mi Sucursal"; el frontend envía GET /api/v1/reservas/sucursal y lista las pendientes. 2. Selecciona una reserva 'Solicitada' y pulsa "Preparar Prendas". 3. El backend valida y cambia el estado a 'Preparada', asigna id_encargado y fecha_preparada, y registra la bitácora. 4. El Cliente acude al vestidor; el Encargado pulsa "Confirmar Recepción". 5. El backend valida estado 'Preparada' y cambia a 'En tienda' con fecha_atendida = NOW(), registrando la bitácora. 6. El Cliente prueba las prendas; si desea comprar, el Encargado registra la venta (CU36) que libera el stock por línea de venta. 7. Al terminar, el Encargado pulsa "Finalizar Atención". 8. El backend valida estado 'En tienda' y cambia a 'Cumplida'; si no hubo venta, libera el stock reservado por cada ítem con su movimiento de Kardex inverso. 9. Retorna 200 y actualiza el badge de pendientes en el menú.
POST CONDICIÓN | La reserva quedó en estado 'Cumplida' con id_encargado, fecha_preparada y fecha_atendida registradas. El stock quedó coherente: liberado vía movimientos inversos si el Cliente no compró, o sustituido por los movimientos de venta (CU36/CU39) si compró. Todos los cambios de estado quedaron en bitácora con old_data/new_data, IP y user agent. La reserva pasa al histórico y deja de contar como pendiente.
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos. Sesión sin gestionar_reservas o de otra sucursal → HTTP 403 { message: "No tienes permisos para gestionar reservas de esta sucursal." }. - E2: Sesión expirada/inválida → HTTP 401; AuthContext redirige a /login. - E3: Reserva no encontrada → HTTP 404 { message: "Reserva no encontrada." }. - E4: Transición de estado inválida. ## CU46 — Emitir Alertas Críticas (quiebres de stock, reservas sin atender)

CASO DE USO | CU46 - Emitir Alertas Críticas (quiebres de stock, reservas sin atender)
--- | ---
PROPÓSITO | Detectar y comunicar de forma proactiva las situaciones críticas del negocio —quiebres de stock (agotados o bajo el mínimo) y reservas sin atender dentro de su fecha— para que el Administrador y el Encargado intervengan a tiempo, evitando ventas perdidas y mal servicio.
DESCRIPCIÓN | Es un proceso automático del backend NestJS ejecutado por el AlertasCriticasService dentro del ciclo programado del servidor (intervalo de 60 s, mismo patrón del SchedulerService). En cada ciclo: (a) detecta quiebres de stock: SELECT id_ptc, id_sucursal, cantidad_disponible, stock_minimo_alert FROM inventario_stock WHERE cantidad_disponible <= stock_minimo_alert AND id_sucursal IN (activas), clasificando cada registro como 'Sin stock' si cantidad_disponible = 0 o 'Stock bajo' si cantidad_disponible > 0, y devuelve el detalle con producto, talla, color y categoría (JOIN producto_talla_color/productos/tallas/colores/categorias); (b) detecta reservas sin atender: SELECT id_reserva, id_sucursal, fecha_reserva, hora_reserva FROM reservas WHERE estado IN ('Solicitada','Preparada') AND fecha_creacion <= NOW() - INTERVAL '120 minutes' (o que fecha_reserva <= hoy) ordenadas por antigüedad; (c) para las alertas con configuración en alertas_stock_config con notificar_email = true, y solo si ultima_notificacion no se emitió en las últimas 24 h, envía el correo al encargado de la sucursal (SMTP configurado) y actualiza ultima_notificacion = NOW(); si SMTP no está configurado, no envía correo pero la alerta sigue visible en el sistema; (d) consolida el resultado en memoria (caché de corta duración) y expone GET /api/v1/admin/alertas/criticas con Authorization: Bearer {access_token}, que devuelve { quiebres: { total, items }, reservas_sin_atender: { total, items } }; (e) al consultar, registra en bitacora_auditoria accion_sql 'SELECT', tabla 'inventario_stock' (o 'reservas'), new_data { alertas: n } con IP y user agent (lectura trazable). En React, el ítem "Alertas Críticas" (solo visible con permiso "*" o consultar_inventario del Encargado) del menú lateral muestra un badge rojo con el total detectado (equivale al esquema de badges de CU25/CU27) que se refresca con polling de 60 s; la página /admin/alertas/criticas lista ambas secciones con el estado de cada ítem. La resolución es automática: un quiebre desaparece cuando el inventario supera el umbral (CU22 recepción, CU24 ajuste o CU39 devolución) y una reserva sin atender deja de contar cuando se prepara/atiende (CU31) o se cancela (CU29); el badge se recalcula en el siguiente ciclo.
ACTORES | Sistema (backend, proceso programado) como generador de alertas. Administrador (permiso "*") y Encargado de Sucursal (permiso gestionar_inventario/gestionar_reservas) como receptores. Encargado/Sucursal recibe el correo opcional si está configurado.
ACTOR INICIADOR | El proceso automático del servidor en cada ciclo de ejecución; los usuarios actúan como receptores y resolutores de la alerta.
PRECONDICIÓN | - El servidor NestJS está corriendo con el ciclo programado activo (intervalo de 60 s). - Existen las tablas inventario_stock (con stock_minimo_alert y cantidad_disponible), alertas_stock_config, reservas, producto_talla_color, productos, tallas, colores y categorias. - Existe al menos una sucursal activa con datos. - El usuario que consulta tiene sesión JWT válida con permiso "*" (Administrador) o gestionar_inventario/gestionar_reservas (Encargado).
FLUJO PRINCIPAL (Camino Feliz) | 1. El ciclo programado del servidor se ejecuta cada 60 s. 2. Detecta los quiebres de stock (cantidad_disponible <= stock_minimo_alert) con su detalle y las reservas 'Solicitada'/'Preparada' vencidas o sin atender. 3. Consolida el resultado en caché de corta duración y, si aplica, envía el correo de aviso (una vez por configuración cada 24 h). 4. El Administrador o Encargado abre la plataforma; el menú lateral muestra el badge rojo con el total de alertas activas. 5. Abre /admin/alertas/criticas; el frontend llama GET /api/v1/admin/alertas/criticas y muestra las dos secciones (Quiebres de stock y Reservas sin atender) con producto/talla/color/sucursal/estado y reserva/sucursal/fecha/antigüedad respectivamente. 6. El encargado actúa: reabastece la prenda (CU22), ajusta inventario (CU24), atiende la reserva (CU31) o el Cliente la cancela (CU29). 7. En el siguiente ciclo la alerta desaparece y el badge se recalcula.
POST CONDICIÓN | Las situaciones críticas quedan visibles en tiempo real para Administración y sucursal con su badge de conteo, permitiendo intervenir antes de perder ventas o desatender clientes. Las alertas se autorresuelven al normalizarse el stock o atenderse/cancelarse las reservas, y la consulta queda trazada en bitácora.
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos. Sesión sin los permisos correspondientes (Administrador "*"/Encargado gestionar_inventario o gestionar_reservas) → HTTP 403 { message: "No tienes permisos para consultar alertas." }; el ítem del menú no aparece y el acceso por URL directa muestra "Acceso denegado". - E2: Sesión expirada/inválida → HTTP 401; redirige a /login. - E3: SMTP no configurado o correo fallido → la alerta sigue activa en el sistema y el error se registra en api-server.err.log (la vía oficial es el badge y el módulo de alertas). - E4: Sin alertas activas → HTTP 200 con { quiebres: { total: 0, items: [] }, reservas_sin_atender: { total: 0, items: [] } } y el frontend muestra el estado vacío "Sin alertas críticas. Todo en orden." sin badge. - E5: Falla en el ciclo programado (consulta con error) → se registra en api-server.err.log y se reintenta en el siguiente ciclo sin perder la operatividad. - E6: Error de red en el polling → el frontend conserva el último badge y reintenta en el siguiente ciclo.
