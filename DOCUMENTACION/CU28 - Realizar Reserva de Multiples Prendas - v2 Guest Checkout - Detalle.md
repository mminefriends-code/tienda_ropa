## CU28 — Realizar Reserva de Múltiples Prendas (Flujo con sesión opcional hasta confirmar)

CASO DE USO | CU28 - Realizar Reserva de Múltiples Prendas (Flujo con sesión opcional hasta confirmar)
--- | ---
PROPÓSITO | Permitir al Cliente reservar varias prendas para probarlas en la sucursal física que elija, permitiéndole **navegar el catálogo y armar la reserva sin iniciar sesión** (modo invitado) y exigiendo la cuenta **solo al confirmar** (login/registro al momento del checkout), siguiendo el patrón guest checkout de los e-commerce (Nordstrom "Reserve & Try In Store", Shopify).
DESCRIPCIÓN | El Cliente puede entrar al catálogo público (CU16) sin sesión y, sobre cualquier prenda, pulsar **"Reservar para probar"**; esto preselecciona la talla y el color (id_ptc) y abre la ruta `/reservas/nueva`, que **queda accesible sin autenticarse** (modo invitado). La página muestra el formulario: sucursal de retiro (estado 'Activo'), fecha (fecha_reserva) y hora (hora_reserva) dentro del horario de sucursal_horarios, más el buscador y el catálogo desde el cual se agregan las prendas al panel "Tu reserva" (talla, color, cantidad). Los GET /api/v1/reservas/opciones y /api/v1/reservas/disponibilidad/{id_sucursal} pasan a ser **públicos** (sin JWT), ya que consultan datos de consulta pública del catálogo. Al pulsar **"Confirmar Reserva"**: si el Cliente **no está autenticado**, el frontend guarda el borrador (sucursal, fecha, hora, items) y redirige a `/login?redirect=/reservas/nueva` con el aviso "Inicia sesión o regístrate para confirmar tu reserva."; tras autenticarse o registrarse (CU01/CU02) vuelve a `/reservas/nueva`, restaura el borrador y procede. Si está autenticado (o ya volvió del login), envía POST /api/v1/reservas con Authorization: Bearer {access_token} y body { "id_sucursal": number, "fecha_reserva": "YYYY-MM-DD", "hora_reserva": "HH:MM:SS", "items": [ { "id_ptc": number, "cantidad": number } ] }. El backend NestJS ReservasService.crearReserva() permanece **idéntico al flujo verificado**: (a) valida el token y el permiso gestionar_reservas en roles.permisos_json (leído de la DB en cada request); (b) valida clientes.id_cliente vía clientes.usuario_id, sucursal 'Activo', fecha no pasada y hora dentro del horario; (c) por cada ítem valida id_ptc y que inventario_stock.cantidad_disponible >= cantidad para (id_ptc, id_sucursal); (d) inserta reservas { estado: 'Solicitada', fecha_creacion: NOW() } con RETURNING id_reserva; (e) inserta los reserva_items obtenidos; (f) actualiza inventario_stock: cantidad_reservada += cantidad y cantidad_disponible -= cantidad; (g) inserta en movimientos_inventario tipo 'Reserva' con cantidad negativa y id_reserva (el trigger recalcula cantidad_disponible); (h) registra en bitacora_auditoria accion_sql 'INSERT', tabla 'reservas', id_registro y new_data con IP y user agent; (i) retorna HTTP 201 con el código y el detalle. El botón "Confirmar Reserva" queda en loading (deshabilitado) durante todo el proceso para evitar reservas duplicadas.
ACTORES | Cualquier visitante del sitio (sin sesión) para consultar el catálogo y armar el borrador. Cliente autenticado (permiso gestionar_reservas) para confirmar la reserva. Encargado de Sucursal y Administrador solo para seguimiento y preparación (CU29/CU30). Cualquier otro rol: sin acceso a la confirmación (403).
ACTOR INICIADOR | Visitante del sitio que desea asegurar varias prendas para probarlas en una sucursal física, con o sin sesión iniciada.
PRECONDICIÓN | - Acceso público a la ruta /reservas/nueva, a GET /api/v1/reservas/opciones y a GET /api/v1/reservas/disponibilidad/{id_sucursal} (sin JWT) para armar el borrador. - Para **confirmar**: el Cliente tiene sesión activa con JWT válido y permiso gestionar_reservas en roles.permisos_json (con soporte de comodín "*"). - Existe el registro en clientes (clientes.id_cliente) vinculado a usuarios.id mediante clientes.usuario_id. - Las tablas reservas, reserva_items, inventario_stock, movimientos_inventario, producto_talla_color, productos, tallas, colores, sucursales y sucursal_horarios existen en el esquema. - La sucursal seleccionada tiene estado 'Activo' y horario definido en sucursal_horarios para el día elegido. - Cada id_ptc seleccionado existe y su inventario_stock de la sucursal tiene cantidad_disponible >= cantidad solicitada al momento de confirmar.
FLUJO PRINCIPAL (Camino Feliz) | 1. El visitante entra a la tienda y navega el catálogo público (CU16) sin iniciar sesión. 2. En una prenda pulsa **"Reservar para probar"**; el sistema abre /reservas/nueva con talla, color y cantidad preseleccionados (puede repetirlo desde el propio catálogo de la página de reserva). 3. Selecciona la sucursal donde quiere probar; el sistema carga sus horarios; elige fecha y hora dentro del horario. 4. Agrega o quita prendas con su cantidad; el panel "Tu reserva" acumula los ítems y muestra el total estimado. 5. Pulsa **"Confirmar Reserva"**. 6a. Si **no está autenticado**: el frontend guarda el borrador, redirige a `/login?redirect=/reservas/nueva` con el aviso de que debe iniciar sesión o registrarse; tras autenticarse/registrarse (CU01/CU02) vuelve a /reservas/nueva, restaura el borrador y continúa en el paso 7. 6b. Si **ya está autenticado**: continúa directo al paso 7. 7. El frontend valida los campos y envía POST /api/v1/reservas con Authorization: Bearer {access_token} y el body con id_sucursal, fecha_reserva, hora_reserva e items. 8. El backend valida permisos, sucursal/fecha/hora, ítems y stock; inserta la reserva 'Solicitada' con sus reserva_items; actualiza el inventario (cantidad_reservada +, cantidad_disponible −) y registra el movimiento de Kardex tipo 'Reserva' y la bitácora. 9. Retorna 201; el frontend muestra el código y los datos de la reserva y limpia el borrador. 10. La reserva queda visible en "Mis Reservas" (CU29) y se notifica a la sucursal (CU30).
POST CONDICIÓN | La reserva quedó creada con estado 'Solicitada' y su detalle en reserva_items, vinculada al Cliente autenticado (reservas.id_cliente). El inventario de la sucursal quedó actualizado (cantidad_reservada incrementada y cantidad_disponible decrementada) y se registró el movimiento de Kardex tipo 'Reserva' trazable al id_reserva. La reserva es visible para el Cliente (CU29) y para el Encargado (CU30/CU31). La bitácora de auditoría registra la creación con old_data/new_data, IP y user agent. El borrador temporal se elimina tras confirmar (o se descarta al salir).
EXCEPCIONES (Flujo Secundario) | - E1: Sin permisos para confirmar. Sesión sin gestionar_reservas → HTTP 403 { message: "No tienes permisos para realizar reservas." }; el módulo no aparece en el menú del Cliente y el acceso por URL directa al módulo autenticado muestra "Acceso denegado". En modo invitado el visitante puede armar el borrador, pero al confirmar se le exige iniciar sesión. - E2: Sesión expirada/inválida. Al confirmar o al volver del login el token no es válido → HTTP 401; AuthContext limpia sesión y redirige a /login (sin perder el borrador guardado). - E3: Sin ítems. items vacío o nulo → HTTP 422 { message: "Debes seleccionar al menos una prenda." }. - E4: Ítem inválido. id_ptc inexistente → 422 { message: "Prenda no encontrada." }; cantidad <= 0 → 422 { message: "La cantidad debe ser mayor a cero." }; prenda con estado_stock 'Sin stock' o producto inactivo → 409 { message: "La prenda [nombre] no está disponible actualmente." }. - E5: Stock insuficiente. Para algún ítem cantidad > cantidad_disponible (incluso si cambió mientras el cliente estuvo en el login) → HTTP 409 { message: "Stock insuficiente de la prenda [nombre] (talla, color). Disponible: X." }; la transacción se revierte completa (rollback). - E6: Sucursal/fecha/hora inválidas. Sucursal inactiva → 422 { message: "La sucursal seleccionada no está disponible para reservas." }; fecha anterior a hoy → 422 { message: "La fecha de la reserva no puede ser anterior a hoy." }; hora fuera del horario → 422 { message: "La hora seleccionada está fuera del horario de atención de la sucursal." }. - E7: Error de red/servidor. Backend sin respuesta → "Error de conexión. Verifica tu acceso a internet e intenta de nuevo." sin dejar la reserva a medias. - E8: Doble envío. El botón "Confirmar Reserva" queda en loading (deshabilitado) mientras se procesa (y durante la redirección al login) para evitar reservas duplicadas. - E9: Borrador obsoleto. Al volver del login se recargan opciones y disponibilidad; si una prenda perdió stock o el horario cambió, se muestra aviso y se pide ajustar antes de confirmar (el backend igualmente revalida con E5).
