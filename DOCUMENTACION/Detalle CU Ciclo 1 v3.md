## CU07 — Registrar Nuevo Empleado

CASO DE USO | CU07 - Registrar Nuevo Empleado (Administrador, Encargado, Cajero)
--- | ---
PROPÓSITO | Permitir al Administrador General crear cuentas de acceso para el personal de la cadena Tiendas Montaño (encargados de sucursal, cajeros, otros administradores), definiendo su rol, sucursal asignada y credenciales iniciales, y activando el flujo de establecimiento de primera contraseña (CU06).
DESCRIPCIÓN | Desde el módulo "Usuarios" (/admin/usuarios en web Angular, AdminUsersScreen en Flutter móvil), el Administrador presiona "Nuevo Empleado". Se abre un MatDialog (web) o showDialog (móvil) con formulario: nombre completo (MatInput text / TextFormField, requerido, minLength=2), correo electrónico (MatInput email / TextFormField con keyboardType: TextInputType.emailAddress, requerido, formato válido, único — validación async debounce 500ms contra backend), teléfono (MatInput tel / TextFormField con keyboardType: TextInputType.phone, requerido, formato +591 XXXXXXX), sucursal asignada (MatSelect / DropdownButtonFormField, requerido — carga dinámicamente desde GET /api/v1/admin/sucursales?estado=Activa), rol (MatSelect / DropdownButtonFormField, requerido — opciones: 'Administrador', 'Encargado', 'Cajero'), y contraseña temporal (generada automáticamente por el backend con formato "Tmp#XXXXXX" — 6 caracteres alfanuméricos + especial — visible en campo con botón "ojo" MatSuffixIcon / IconButton con icon eye/eye_off; el Administrador puede modificarla). El botón "Registrar Empleado" se deshabilita (MatDisabled / AbsorbPointer) hasta que todos los campos obligatorios sean válidos. Al presionar "Registrar Empleado", el frontend envía POST /api/v1/admin/empleados con header Authorization: Bearer {access_token} y body JSON { "nombre": string, "email": string, "telefono": string, "sucursal_id": int, "rol": string, "password_temporal": string }. El endpoint admin.registrar_empleado ejecuta: (a) verifica que el usuario autenticado tenga permiso 'gestionar_usuarios' en roles.permisos_json (middleware FastAPI @require_permission("gestionar_usuarios")); si no tiene, retorna HTTP 403; (b) valida que usuarios.email no exista previamente: SELECT COUNT(*) FROM usuarios WHERE email = :email; si existe, retorna HTTP 409 con { "detail": "Ya existe un usuario con este correo electrónico." }; (c) hashea la contraseña temporal con bcrypt.hash(password_temporal, rounds=12); (d) INSERT en usuarios: { email, password_hash: hash, nombre, rol, estado: 'Pendiente', intentos_fallidos: 0, fecha_creacion: NOW(), fecha_ultimo_acceso: NULL }; (e) captura usuario_id = lastval(); (f) INSERT en usuarios_empleados: { usuario_id, sucursal_id, rol }; (g) genera token = uuid_v4() y INSERT en first_password_tokens: { usuario_id, token, expires_at: NOW() + 24 horas, used: false, created_at: NOW() }; (h) envía email transaccional a email con asunto "Bienvenido a Tiendas Montaño — Establece tu contraseña" y enlace https://tiendasmontano.com/establecer-contraseña?token={token}; (i) INSERT en bitacora_auditoria: { accion_sql: 'INSERT', tabla_afectada: 'usuarios_empleados', usuario_id: admin_id, registro_id: usuario_id, ip_address: request.client.host, user_agent: request.headers['user-agent'], new_data: { nombre, email, sucursal_id, rol, password_temporal_visible: password_temporal } }; (j) retorna HTTP 201 con { "detail": "Empleado registrado exitosamente.", "empleado_id": int }. En el frontend web (Angular), el AdminUsersComponent cierra el MatDialog y recarga la tabla con GET /api/v1/admin/empleados. El nuevo empleado aparece con badge "Pendiente" (MatBadge, color amarillo). En Flutter, se muestra un SnackBar con duración 4 segundos. Si el servicio de correo falla (SMTP timeout, credenciales inválidas), el empleado se registra igualmente en la BD pero el sistema muestra una alerta al Administrador: "Empleado registrado pero no se pudo enviar el email de bienvenida a [email]. Puede reenviar la invitación manualmente." con botón "Reenviar Invitación" que ejecuta POST /api/v1/admin/empleados/{id}/reenviar-invitation.
ACTORES | Administrador General.
ACTOR INICIADOR | Administrador que necesita agregar personal a la plataforma Tiendas Montaño.
PRECONDICIÓN | - El Administrador debe tener sesión activa con JWT válido y permiso 'gestionar_usuarios' en roles.permisos_json (verificado por el middleware de autorización FastAPI @require_permission("gestionar_usuarios")). - Debe existir al menos una sucursal en la tabla sucursales con estado = 'Activa'. La tabla sucursales debe tener: id (serial PK), nombre (varchar), direccion (varchar), ciudad_id (FK → ciudades.id), telefono (varchar), horario_apertura (time), horario_cierre (time), estado ('Activa'/'Inactiva'). - La tabla usuarios_empleados debe existir con: id (serial PK), usuario_id (FK → usuarios.id UNIQUE), sucursal_id (FK → sucursales.id), rol (varchar). - La tabla first_password_tokens debe existir con: id (serial PK), usuario_id (FK → usuarios.id), token (UUID UNIQUE), expires_at (timestamp), used (boolean DEFAULT false), created_at (timestamp). - Debe haber un servicio de correo transaccional configurado (SMTP o API de envío).
FLUJO PRINCIPAL (Camino Feliz) | 1. El Administrador navega a Usuarios (ruta /admin/usuarios en web Angular, AdminUsersScreen en Flutter). 2. El sistema ejecuta GET /api/v1/admin/empleados con header Authorization: Bearer {access_token}. 3. Backend verifica permiso 'gestionar_usuarios'. OK. 4. Backend retorna lista de empleados con datos de usuarios JOIN usuarios_empleados JOIN sucursales. 5. Frontend renderiza tabla de empleados con columnas: Nombre, Email, Teléfono, Sucursal, Rol, Estado (badge), Último Acceso. 6. El Administrador presiona el botón "Nuevo Empleado" (MatFab / FloatingActionButton con icon +person). 7. Se abre MatDialog / showDialog con formulario vacío. 8. Ingresa nombre = "Carlos Pérez". Validación: minLength=2 ✓ → borde verde. 9. Ingresa email = "carlos@tiendasmontano.com". Validación: formato email ✓, consulta async debounce 500ms GET /api/v1/admin/empleados/check-email?email=carlos@tiendasmontano.com → "Disponible" ✓. 10. Ingresa teléfono = "+59171234568". Validación: formato +591 XXXXXXX ✓. 11. Selecciona sucursal = "Sucursal Centro" (cargada dinámicamente desde GET /api/v1/admin/sucursales?estado=Activa en ngOnInit/initState). 12. Selecciona rol = "Encargado" (select con opciones: Administrador, Encargado, Cajero). 13. El campo contraseña muestra la temporal "Tmp#xK2mQ9" generada por el backend al abrir el modal (GET /api/v1/admin/empleados/generate-temp-password → retorna { "password": "Tmp#xK2mQ9" }). El Administrador puede modificarla. Botón "ojo" permite mostrar/ocultar. 14. Todos los campos obligatorios son válidos → botón "Registrar Empleado" se habilita. 15. Presiona "Registrar Empleado". 16. Frontend envía POST /api/v1/admin/empleados con header Authorization: Bearer {access_token} y body { nombre: "Carlos Pérez", email: "carlos@tiendasmontano.com", telefono: "+59171234568", sucursal_id: 1, rol: "Encargado", password_temporal: "Tmp#xK2mQ9" }. 17. Backend verifica que email no exista en usuarios WHERE email = 'carlos@tiendasmontano.com'. No existe → OK. 18. Backend crea hash = bcrypt.hash("Tmp#xK2mQ9", 12). 19. Backend INSERT en usuarios: { email: "carlos@tiendasmontano.com", password_hash: hash, nombre: "Carlos Pérez", rol: "Encargado", estado: 'Pendiente', intentos_fallidos: 0, fecha_creacion: NOW(), fecha_ultimo_acceso: NULL }. 20. Backend captura usuario_id = lastval(). 21. Backend INSERT en usuarios_empleados: { usuario_id, sucursal_id: 1, rol: "Encargado" }. 22. Backend genera token = uuid_v4() y INSERT en first_password_tokens: { usuario_id, token, expires_at: NOW() + INTERVAL '24 hours', used: false, created_at: NOW() }. 23. Backend envía email a carlos@tiendasmontano.com con asunto "Bienvenido a Tiendas Montaño — Establece tu contraseña" y enlace https://tiendasmontano.com/establecer-contraseña?token={token}. 24. Backend INSERT en bitacora_auditoria: { accion_sql: 'INSERT', tabla_afectada: 'usuarios_empleados', usuario_id: admin_id, registro_id: usuario_id, ip_address: request.client.host, user_agent: request.headers['user-agent'], new_data: { nombre: "Carlos Pérez", email: "carlos@tiendasmontano.com", sucursal: "Sucursal Centro", rol: "Encargado" } }. 25. Backend retorna HTTP 201 con { "detail": "Empleado registrado exitosamente.", "empleado_id": usuario_id }. 26. Frontend muestra toast "Empleado Carlos Pérez registrado. Se envió un email de bienvenida." y cierra el MatDialog. 27. La tabla de empleados se recarga. Carlos aparece con badge "Pendiente" (amarillo).
POST CONDICIÓN | Existe un registro en usuarios (estado='Pendiente') y en usuarios_empleados vinculando al empleado con su sucursal y rol. Se envió email de bienvenida con enlace para CU06. El empleado no puede iniciar sesión hasta completar CU06 (establecer primera contraseña) que cambia estado a 'Activo'.
EXCEPCIONES (Flujo Secundario) | - E1: Email ya registrado. Si usuarios.email ya existe en la tabla usuarios, el backend retorna HTTP 409 con { "detail": "Ya existe un usuario con este correo electrónico." }. El frontend muestra toast de error (color rojo, duración 5s), coloca foco en el campo email con borde rojo y el mensaje "Este correo ya está registrado" debajo del campo. No se revela si el empleado está activo o pendiente (seguridad). Se inserta en bitacora_auditoria: { accion_sql: 'REGISTER_EMPLOYEE_FAILED', tabla_afectada: 'usuarios', usuario_id: admin_id, ip_address, new_data: { email: email, razon: 'Email duplicado' } }. - E2: Sucursal inexistente. Si sucursal_id no existe en la tabla sucursales (posible manipulación del select), el backend retorna HTTP 400 con { "detail": "La sucursal seleccionada no es válida." }. El frontend muestra error en el campo sucursal y recarga la lista de sucursales. - E3: Email de bienvenida fallido. Si el servicio de correo retorna error (SMTP timeout >10s, credenciales inválidas, mailbox not found), el backend registra el empleado en la BD igualmente (las tablas usuarios y usuarios_empleados quedan creadas) pero retorna HTTP 207 con { "detail": "Empleado registrado pero no se pudo enviar el email de bienvenida a [email]. Puede reenviar la invitación manualmente desde la lista de empleados." }. El frontend muestra una alerta amarilla (MatSnackBar con panelClass='snack-warn') con el mensaje y un botón "Reenviar Invitación" que ejecuta POST /api/v1/admin/empleados/{id}/reenviar-invitation. - E4: Sin permisos. Si el usuario autenticado no tiene permiso 'gestionar_usuarios' en roles.permisos_json, el módulo "Usuarios" no aparece en el menú lateral (el componente SidebarComponent filtra por permisos). Si el usuario accede vía URL directa (/admin/usuarios), el layout protegido (LayoutAdminComponent con guard AdminGuard en app-routing.module.ts) verifica permisos y redirige a /inicio. En móvil, el Drawer del menú no muestra la entrada "Usuarios". - E5: Contraseña temporal débil. Si el Administrador modifica la contraseña temporal generada y no cumple las reglas de fortaleza (mín. 8 caracteres, 1 mayúscula, 1 minúscula, 1 número, 1 carácter especial [!@#$%^&*]), el frontend muestra debajo del campo: "La contraseña debe tener al menos 8 caracteres, una mayúscula, una minúscula, un número y un carácter especial (!@#$%^&*)." con borde rojo. El botón "Registrar Empleado" permanece deshabilitado. - E6: Error de servidor (HTTP 500). Si el backend falla por excepción no controlada, el frontend muestra toast "Error al registrar el empleado. Intenta de nuevo en unos momentos." con botón "Reintentar".
CASOS DE USO RELACIONADOS | CU06 (Establecer Primera Contraseña — flujo posterior del empleado), CU08 (Asignar/Modificar Roles y Permisos — define qué puede hacer el rol asignado), CU01 (Iniciar Sesión — cuando el empleado complete CU06), CU12 (Sucursales — fuente de la lista de sucursales).

## CU08 — Asignar/Modificar Roles y Permisos

CASO DE USO | CU08 - Asignar/Modificar Roles y Permisos
--- | ---
PROPÓSITO | Permitir al Administrador General definir y ajustar los permisos de acceso de cada rol del sistema (RBAC — Role-Based Access Control), controlando qué módulos, rutas y acciones puede ejecutar cada tipo de usuario, manteniendo la trazabilidad de cada cambio en la bitácora de auditoría.
DESCRIPCIÓN | Desde el módulo "Configuración → Roles y Permisos" (/admin/roles en web Angular, AdminRolesScreen en Flutter móvil), el Administrador visualiza una grilla/matriz de roles × permisos usando un MatTable (web) o DataTable (Flutter). Los roles son: Administrador, Encargado, Cajero, Cliente. Los permisos representan módulos y acciones: gestionar_usuarios, gestionar_sucursales, gestionar_catalogo, gestionar_proveedores, gestionar_compras, ver_inventario, editar_inventario, gestionar_reservas, gestionar_ventas, ver_reportes, configuracion, auditoria, respaldos. El rol "Administrador" tiene todos los permisos marcados y deshabilitados (checkbox MatCheckbox / CheckboxListTile checked y disabled, color gris; no se puede modificar). Los demás roles son editables. Cada celda de la grilla es un checkbox. Al presionar "Guardar Cambios", el frontend envía PUT /api/v1/admin/roles con header Authorization: Bearer {access_token} y body JSON { "rol_id": int, "permisos": string[] }. El endpoint admin.actualizar_rol ejecuta: (a) verifica permiso 'configuracion'; (b) valida que permisos sea un array no vacío; (c) consulta el rol por id: SELECT id, nombre_rol, permisos_json FROM roles WHERE id = :rol_id; si no existe, HTTP 404; (d) valida que nombre_rol != 'Administrador' (protección del rol Admin); (e) compara permisos_json anterior (old_data) con los nuevos (new_data); (f) UPDATE roles SET permisos_json = :permisos WHERE id = :rol_id; (g) INSERT bitacora_auditoria con old_data y new_data; (h) HTTP 200 con mensaje de éxito. Los usuarios con el rol modificado conservan su JWT con los permisos anteriores hasta su próximo login (el JWT contiene los permisos del momento del login; el AuthGuard en cada request evalúa los permisos del JWT, no de la BD).
ACTORES | Administrador General.
ACTOR INICIADOR | Administrador que necesita ajustar los permisos de acceso de un rol para reflejar cambios en la estructura organizacional o en las responsabilidades del cargo.
PRECONDICIÓN | - El Administrador debe tener sesión activa con permiso 'configuracion' en roles.permisos_json (evaluado por middleware FastAPI). - La tabla roles debe existir con: id (serial PK), nombre_rol (varchar UNIQUE), permisos_json (JSONB array de strings), descripcion (text). - Deben existir los 4 roles base: Administrador (todos los permisos), Encargado (mayoría), Cajero (inventario y ventas), Cliente (catálogo y compras). El seed inicial se realiza en la migración de base de datos (Alembic o scripts SQL).
FLUJO PRINCIPAL (Camino Feliz) | 1. El Administrador navega a Configuración → Roles y Permisos (ruta /admin/roles). 2. El sistema ejecuta GET /api/v1/admin/roles con header Authorization: Bearer {access_token}. 3. Backend retorna la lista de roles con sus permisos_json: [{ "id": 1, "nombre_rol": "Administrador", "permisos_json": ["gestionar_usuarios", "gestionar_sucursales", ...todos], "descripcion": "Acceso total al sistema" }, { "id": 2, "nombre_rol": "Encargado", "permisos_json": ["ver_inventario", "editar_inventario", ...], ... }, ...]. 4. Frontend renderiza la grilla: filas = roles, columnas = 13 permisos disponibles. 5. Los permisos de la fila "Administrador" están checked y disabled (MatCheckbox disabled + color text-muted). 6. El Administrador selecciona la fila "Cajero". 7. Activa los permisos: ver_inventario, gestionar_ventas, gestionar_reservas, gestionar_catalogo (checks). Desactiva: gestionar_proveedores, gestionar_compras, configuracion, auditoria, respaldos, gestionar_usuarios, gestionar_sucursales (unchecks). 8. Presiona "Guardar Cambios". 9. Frontend envía PUT /api/v1/admin/roles con { "rol_id": 3, "permisos": ["ver_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"] }. 10. Backend valida que permisos sea un array no vacío. OK. 11. Backend consulta roles WHERE id = 3: { id: 3, nombre_rol: "Cajero", permisos_json: ["ver_inventario", "editar_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"] }. 12. Backend compara: old_data = ["ver_inventario", "editar_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"], new_data = ["ver_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"]. Hay cambios (se quitó "editar_inventario"). 13. Backend UPDATE roles SET permisos_json = '["ver_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"]' WHERE id = 3 AND nombre_rol != 'Administrador'. OK (nombre_rol es "Cajero"). 14. Backend INSERT en bitacora_auditoria: { accion_sql: 'UPDATE', tabla_afectada: 'roles', usuario_id: admin_id, registro_id: 3, old_data: { permisos_anterior: ["ver_inventario", "editar_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"] }, new_data: { permisos_nuevo: ["ver_inventario", "gestionar_ventas", "gestionar_reservas", "gestionar_catalogo"] }, ip_address: request.client.host, user_agent: request.headers['user-agent'] }. 15. Retorna HTTP 200 con { "detail": "Permisos del rol Cajero actualizados. Los cambios se aplicarán en el próximo inicio de sesión de los usuarios afectados." }. 16. Frontend muestra toast de éxito y recarga la grilla. 17. Los cajeros activos conservan su JWT con los permisos anteriores hasta cerrar sesión y volver a iniciar (el JWT contiene los permisos del momento del login, no se invalida en tiempo real).
POST CONDICIÓN | Los permisos del rol quedan actualizados en roles.permisos_json. Los usuarios con ese rol conservan su JWT con los permisos anteriores hasta su próximo login (ciclo de vida del JWT: 8 horas para access_token). La bitácora registra los permisos anterior y nuevo para auditoría completa.
EXCEPCIONES (Flujo Secundario) | - E1: Intento de modificar rol Administrador. El backend valida que nombre_rol != 'Administrador' antes de ejecutar el UPDATE. Si se intenta (manipulación del JSON del frontend), el backend retorna HTTP 403 con { "detail": "El rol Administrador tiene acceso total del sistema y no puede ser modificado." }. Los checkboxes de la fila Administrador están disabled en el frontend (MatCheckbox disabled), por lo que la interacción visual es imposible. Se registra en bitacora_auditoria: { accion_sql: 'UPDATE_FAILED', new_data: { razon: 'Intento de modificar rol Administrador' } }. - E2: Permisos vacíos. Si el usuario desactiva todos los permisos de un rol, el frontend muestra "Un rol debe tener al menos un permiso habilitado." debajo de la grilla con borde rojo, y deshabilita el botón "Guardar Cambios" (MatDisabled). El backend también valida: si el array está vacío, retorna HTTP 400 con { "detail": "Un rol debe tener al menos un permiso habilitado." }. - E3: Sin permisos de configuración. Si el usuario no tiene permiso 'configuracion', el módulo "Roles y Permisos" no aparece en el menú lateral (SidebarComponent filtra). Si accede vía URL directa (/admin/roles), el AdminGuard redirige a /inicio con toast "No tienes acceso a esta sección." - E4: Error de integridad. Si el rol_id no existe en la tabla roles, HTTP 404 con { "detail": "Rol no encontrado." }. Si el JSON de permisos es inválido (no es un array de strings), HTTP 400 con { "detail": "Formato de permisos inválido." }. - E5: Sesión expirada. Si el JWT ya no es válido, HTTP 401 y el AuthGuard redirige a /login con "Tu sesión ha expirado. Inicia sesión nuevamente."
CASOS DE USO RELACIONADOS | CU01 (Iniciar Sesión — los permisos se cargan en el JWT al login), CU07 (Registrar Empleado — se asigna un rol), CU09 (Inhabilitar Empleado — requiere permiso gestionar_usuarios), CU10 (Rehabilitar Empleado — requiere permiso gestionar_usuarios).

## CU09 — Inhabilitar Empleado (Baja Lógica)

CASO DE USO | CU09 - Inhabilitar Empleado (Baja Lógica)
--- | ---
PROPÓSITO | Permitir al Administrador General desactivar la cuenta de un empleado sin eliminarlo físicamente del sistema (baja lógica), impidiendo que pueda iniciar sesión mientras se conserva intacto su historial de acciones en la bitácora de auditoría y en los registros de inventario, ventas y recepciones.
DESCRIPCIÓN | Desde la tabla de empleados (/admin/usuarios en web Angular, AdminUsersScreen en Flutter), el Administrador busca al empleado por nombre o email (MatFormField con MatInput + MatIconPrefix search, con debounce 300ms que ejecuta GET /api/v1/admin/empleados?q={query}), presiona el ícono de acciones (⋮ — MatMenuTrigger / PopupMenuButton) y selecciona "Inhabilitar". Se abre un MatDialog (web) o showDialog (móvil) de confirmación con el mensaje: "¿Estás seguro de inhabilitar a [nombre] ([email])? Esta acción impedirá que [nombre] pueda iniciar sesión en la plataforma. Sus registros históricos se conservarán intactos." Campo opcional: "Motivo de inhabilitación" (MatTextarea / TextFormField multiline, maxLength=500). Botones: "Confirmar Inhabilitación" (MatButton color=warn / ElevatedButton color: Colors.red) y "Cancelar" (MatButton / TextButton). Si confirma, el frontend envía PUT /api/v1/admin/empleados/{id}/inhabilitar con header Authorization: Bearer {access_token} y body JSON { "motivo": string|null }. El endpoint admin.inhabilitar_empleado ejecuta: (a) verifica permiso 'gestionar_usuarios'; (b) consulta el empleado: SELECT u.id, u.estado, u.email, u.nombre FROM usuarios u JOIN usuarios_empleados ue ON u.id = ue.usuario_id WHERE u.id = :id; si no existe, HTTP 404; (c) verifica que u.estado != 'Inactivo' (ya inhabilitado → E1); (d) verifica que id != admin_id (no auto-inhabilitación → E2); (e) UPDATE usuarios SET estado = 'Inactivo', fecha_baja = NOW(), motivo_baja = :motivo WHERE id = :id; (f) INSERT bitacora_auditoria con old_data { estado: 'Activo' } y new_data { estado: 'Inactivo', motivo, fecha_baja: NOW() }; (g) HTTP 200 con { "detail": "Empleado inhabilitado correctamente." }. Si el empleado tenía una sesión JWT activa, esta quedará invalidada en el próximo request al backend: el middleware de autenticación FastAPI, en cada request autenticado, verifica que usuarios.estado = 'Activo'; si es 'Inactivo', retorna HTTP 403 con { "detail": "Tu cuenta ha sido deshabilitada. Contacta al administrador." } y el frontend (el AuthInterceptor) redirige a /login.
ACTORES | Administrador General.
ACTOR INICIADOR | Administrador que necesita desactivar a un empleado por renuncia, despido, licencia u otra razón administrativa.
PRECONDICIÓN | - El Administrador debe tener permiso 'gestionar_usuarios' en roles.permisos_json. - El empleado a inhabilitar debe existir en usuarios_empleados con usuarios.estado = 'Activo'. - El usuario autenticado (Administrador) no puede inhabilitar su propia cuenta desde esta función (el backend valida id != :admin_id). - El empleado puede tener registros activos en inventario, ventas, reservas, etc. Estos no se eliminan ni se alteran (la baja es lógica, no física).
FLUJO PRINCIPAL (Camino Feliz) | 1. El Administrador navega a Usuarios (ruta /admin/usuarios). 2. El sistema ejecuta GET /api/v1/admin/empleados y renderiza la tabla completa. 3. ## CU20 — Evaluar y Puntuar Proveedores (Scoring) — Prioridad Baja

--- | ---
PROPÓSITO | Permitir al Administrador evaluar el desempeño de proveedores según criterios objetivos (% entregas a tiempo, calidad de mercadería, competitividad de precio) y generar un ranking que apoye las decisiones de compra. Prioridad Baja — puede posponerse al Ciclo 3.

ACTOR INICIADOR | Administrador que necesita evaluar proveedores para decidir a cuál asignar una nueva orden de compra.

Backend envía email a admin@tiendasmontano.com y encargado@sucursalcentro.com: asunto "Tiendas Montaño — Alerta de Stock Bajo", cuerpo: "El producto 'Remera Básica Algodón' (Talla M, Color Negro) en Sucursal Centro está por debajo del umbral mínimo. Stock actual: 4. Umbral mínimo: 5. Se recomienda reponer mediante una Orden de Compra (CU21)." 16. Backend actualiza alertas_stock_config.ultima_notificacion = NOW() para respetar el cooldown de 24h.
POST CONDICIÓN | Alertas activas para los productos configurados. Se envían emails automáticos al Administrador y Encargado cuando el stock cae por debajo del umbral (sujeto a cooldown de 24h para no spamear). Provee información para decidir reposiciones (CU21).
EXCEPCIONES (Flujo Secundario) | - E1: Umbral ≤ 0. Si se ingresa un umbral ≤ 0, el frontend muestra "El umbral mínimo debe ser al menos 1." con borde rojo y no guarda. El backend valida: HTTP 400 { "detail": "El umbral mínimo debe ser mayor a 0." }. - E2: Umbral > stock actual (alerta inmediata). CASOS DE USO RELACIONADOS | CU44 (Dashboard — muestra las alertas activas), CU26 (Existencias — el stock que se monitorea), CU22 (Recepción — al subir stock puede desactivarse una alerta), CU21 (Orden de Compra — la alerta recomienda reponer).

## CU26 — Consultar Existencias Consolidadas

CASO DE USO | CU26 - Consultar Existencias Consolidadas
--- | ---
PROPÓSITO | Permitir al Administrador y Encargados ver una vista consolidada del estado de stock de todas las prendas: disponibles, reservadas, vendidas, agotadas y próximas a ingresar (por orden de compra pendiente), como herramienta para decidir reposiciones y distribución entre sucursales.
DESCRIPCIÓN | Desde /inventario/existencias (web Angular, InventarioExistenciasComponent / Flutter InventarioExistenciasScreen). Tabla (MatTable / DataTable) con columnas: Producto, Talla, Color, Sucursal, Cantidad Disponible, Cantidad Reservada, Cantidad Vendida, Estado (badge: Disponible=verde si cantidad_disponible > umbral, Poco Stock=amarillo si cantidad_disponible ≤ umbral y > 0, Agotado=rojo si cantidad_disponible = 0), Cantidad por Ingresar (suma de cantidades pendientes de órdenes de compra en estado 'Pendiente' para esa combinación). Filtros en barra superior: sucursal (MatSelect — Encargado solo su sucursal), categoría, producto, talla, color, estado (Disponible/Poco Stock/Agotado). Botón "Exportar CSV". La consulta cruza: inventario_stock (cantidad_disponible, cantidad_reservada, cantidad_vendida), producto_talla_color (producto, talla, color), y orden_compra_items JOIN ordenes_compra (para cantidad_por_ingresar = SUM de items de órdenes Pendientes).
ACTORES | Administrador General (todas las sucursales), Encargado de Sucursal (solo su sucursal).
ACTOR INICIADOR | Administrador o Encargado que necesita un panorama de existencias para decidir reposiciones y distribución.
PRECONDICIÓN | - Permiso 'ver_inventario'. - Registros en inventario_stock y movimientos_inventario (CU22, CU24). - Órdenes de compra en estado 'Pendiente' (CU21) para calcular cantidad_por_ingresar.
FLUJO PRINCIPAL (Camino Feliz) | 1. Navega a Inventario → Existencias (ruta /inventario/existencias). 2. Frontend ejecuta GET /api/v1/inventario/existencias con header Authorization: Bearer {access_token}. El backend filtra por sucursal del usuario (si es Encargado) o todas (si Administrador). 3. Backend construye query: SELECT ptc.id, p.nombre as producto, t.nombre as talla, c.nombre as color, s.nombre as sucursal, ist.cantidad_disponible, ist.cantidad_reservada, ist.cantidad_vendida, COALESCE((SELECT SUM(oci.cantidad) - SUM(GREATEST(oci.cantidad - r.cantidad_recibida, 0)) FROM orden_compra_items oci JOIN ordenes_compra oc ON oci.orden_compra_id = oc.id WHERE oci.producto_talla_color_id = ptc.id AND oc.estado = 'Pendiente'), 0) as cantidad_por_ingresar FROM inventario_stock ist JOIN producto_talla_color ptc ON ist.producto_talla_color_id = ptc.id JOIN productos p ON ptc.producto_id = p.id JOIN tallas t ON ptc.talla_id = t.id JOIN colores c ON ptc.color_id = c.id JOIN sucursales s ON ist.sucursal_id = s.id WHERE s.estado = 'Activa' ORDER BY p.nombre, t.nombre, c.nombre. 4. Retorna listado con todas las combinaciones y su stock. 5. Frontend renderiza tabla con colores por estado: "Remera Básica Algodón | M | Negro | Sucursal Centro | Disponible: 12 | Reservada: 2 | Vendida: 30 | Estado: Disponible (verde) | Por ingresar: 50". Otra fila agotada: "… | Disponible: 0 | … | Estado: Agotado (rojo) | Por ingresar: 0". 6. El Administrador filtra por estado = "Poco Stock" para ver qué reponer. 7. Frontend envía GET /api/v1/inventario/existencias?estado=poco_stock. 8. Backend filtra de nuevo (cantidad_disponible > 0 AND cantidad_disponible <= umbral). 9. Retorna solo productos con poco stock. 10. El Administrador decide crear una Orden de Compra (CU21) para los productos que están bajos o agotados. 11. Presiona "Exportar CSV". 12. Descarga "existencias_20260902.csv".
POST CONDICIÓN | El usuario obtiene un panorama completo del estado de existencias de todas las prendas por sucursal, permitiéndole decidir dónde reponer y qué distribuir. La vista alimenta las decisiones de reposición (CU21).
EXCEPCIONES (Flujo Secundario) | - E1: Sin resultados. "No se encontraron existencias con los filtros seleccionados." con estado vacío y botón "Limpiar filtros". - E2: Inventario vacío. Si no hay registros en inventario_stock, "El inventario está vacío. Registra una recepción (CU22) para ingresar stock." con botón que redirige a /sucursal/recepciones. - E3: Sucursal sin permisos (Encargado intenta ver otra). El backend fuerza su sucursal (HTTP 403 si intenta otra). - E4: Error de carga. "No pudimos cargar las existencias. Intenta de nuevo."
CASOS DE USO RELACIONADOS | CU22 (Recepción — ingresa stock), CU23 (Kardex — historial detallado), CU25 (Alertas — umbrales que definen el estado "Poco Stock"), CU44 (Dashboard — muestra existencias resumidas), CU21 (Orden de Compra — para reponer).

## CU27 — Respaldar Información a Storage Externo

CASO DE USO | CU27 - Respaldar Información a Storage Externo
--- | ---
PROPÓSITO | Permitir al Administrador generar copias de seguridad de la base de datos PostgreSQL y almacenarlas en un servicio de cloud storage externo (AWS S3 o similar), como medida de protección contra pérdidas de datos por caída de servidor, corrupción de BD o borrado accidental.
DESCRIPCIÓN | Desde /admin/respaldos (web Angular, AdminRespaldosComponent / Flutter AdminRespaldosScreen), el Administrador ve una tabla (MatTable) de respaldos con columnas: Fecha, Tipo (Manual/Automático), Tamaño (bytes→formato legible: KB/MB/GB), Estado (badge: Exitoso=verde, En Progreso=azul/animation, Fallido=rojo), Ubicación/Almacenamiento (storage_url). Botones: "Crear Respaldo Ahora" (MatFab primary), "Programar Respaldo" (MatButton / OutlinedButton que abre MatDialog con frecuencia: Diario, Semanal, y hora), "Restaurar" (por fila, MatIconButton con icon restore), "Descargar" (por fila, MatIconButton con icon download). Botón "Crear Respaldo Ahora": frontend envía POST /api/v1/admin/respaldos/crear con header Authorization: Bearer {access_token}. El endpoint admin.crear_respaldo ejecuta: (a) verifica permiso 'respaldos'; (b) lanza tarea asíncrona en background (FastAPI BackgroundTasks / Celery): (b1) ejecuta pg_dump de la BD PostgreSQL: pg_dump -U {usuario} -h {host} -d tiendasmontano_db > tiendasmontano_YYYYMMDD_HHMMSS.sql; (b2) comprime con gzip: gzip tiendasmontano_YYYYMMDD_HHMMSS.sql → tiendasmontano_YYYYMMDD_HHMMSS.sql.gz; (b3) sube el archivo a cloud storage (boto3 S3): s3_client.upload_file('tiendasmontano_YYYYMMDD_HHMMSS.sql.gz', 'tiendasmontano-respaldos', 'respaldos/tiendasmontano_YYYYMMDD_HHMMSS.sql.gz'); (b4) guarda metadata; (c) INSERT en respaldos: { fecha: NOW(), tipo: 'Manual', tamano_bytes: tamaño_del_archivo, estado: 'Exitoso', storage_url: 's3://tiendasmontano-respaldos/respaldos/tiendasmontano_YYYYMMDD_HHMMSS.sql.gz' }; (d) INSERT bitacora_auditoria: { accion_sql: 'BACKUP', tabla_afectada: 'respaldos', new_data: { tipo: 'Manual', tamano_bytes, storage_url } }; (e) HTTP 201 con { "detail": "Respaldo creado.", "respaldo_id": int }. La tabla de respaldos se refresca mostrando el nuevo respaldo con estado "Exitoso". Programación automática: los respaldos Diarios/Semanales se ejecutan por el cron job del backend (APScheduler) que llama al mismo endpoint de creación en background, con tipo 'Automático'. Retención configurable: parámetro que elimina respaldos más antiguos que N días (ej: 30) cuando se excede el espacio o por política.
ACTORES | Administrador General.
ACTOR INICIADOR | Administrador que necesita generar o programar copias de seguridad de los datos de Tiendas Montaño.
PRECONDICIÓN | - Permiso 'respaldos' en roles.permisos_json. - Acceso configurado al servicio de storage (AWS S3 bucket 'tiendasmontano-respaldos' o similar con credenciales válidas). - Herramienta pg_dump instalada y disponible en el servidor backend (ruta en PATH). - La tabla respaldos debe existir: id, fecha, tipo ('Manual'/'Automático'), tamano_bytes, estado ('Exitoso'/'In Progreso'/'Fallido'), storage_url, creado_por.
FLUJO PRINCIPAL (Camino Feliz) | 1. Navega a Configuración → Respaldos (ruta /admin/respaldos). 2. GET /api/v1/admin/respaldos retorna lista paginada de respaldos existentes. 3. Renderiza tabla con respaldos previos. 4. Presiona "Crear Respaldo Ahora" (MatFab primary). 5. Frontend envía POST /api/v1/admin/respaldos/crear. 6. Backend verifica permiso 'respaldos'. OK. 7. Backend lanza tarea en background. 8. Backend retorna HTTP 202 Accepted con { "detail": "Respaldo iniciado. Se estará completando en segundo plano.", "respaldo_id": 15 }. 9. INSERT respaldos con estado 'En Progreso'. 10. La tabla muestra el respaldo con estado "En Progreso" (badge azul con spinner). 11. En background, el backend ejecuta pg_dump de la BD → archivo tiendasmontano_20260902_143000.sql. 12. Comprime con gzip → tiendasmontano_20260902_143000.sql.gz (18.5 MB). 13. Sube a S3: s3://tiendasmontano-respaldos/respaldos/tiendasmontano_20260902_143000.sql.gz con ContentType: application/gzip. 14. UPDATE respaldos SET estado = 'Exitoso', tamano_bytes = 19400000, storage_url = 's3://tiendasmontano-respaldos/respaldos/tiendasmontano_20260902_143000.sql.gz' WHERE id = 15. 15. INSERT bitacora_auditoria: { accion_sql: 'BACKUP', tabla_afectada: 'respaldos', new_data: { tipo: 'Manual', tamano_bytes: 19400000, storage_url: 's3://...sql.gz' } }. 16. El frontend, al refrescar (polling cada 5s o WebSocket), actualiza el badge a "Exitoso" (verde) y muestra tamaño "18.5 MB". 17. Toast "Respaldo completado. Tamaño: 18.5 MB."
POST CONDICIÓN | Una copia de seguridad de la base de datos completa (PostgreSQL) quedó almacenada externamente en cloud storage. Puede descargarse o restaurarse en caso de necesidad. La bitácora de auditoría registra la operación.
EXCEPCIONES (Flujo Secundario) | - E1: Error de conexión con storage. Si S3 no es accesible (timeout, credenciales inválidas, bucket no encontrado), el respaldo falla: UPDATE respaldos SET estado = 'Fallido', error_message = 'No se pudo conectar con el servicio de almacenamiento'. El frontend muestra "Respaldo fallido. No se pudo conectar con el servicio de almacenamiento." con estado rojo. La operación se reintenta 2 veces con backoff exponencial (5s, 20s). - E2: Espacio insuficiente. Si el bucket no tiene espacio (quota), "Respaldo fallido. Libera espacio en el servicio de almacenamiento." Se pueden eliminar respaldos antiguos (retención). - E3: Respaldo en progreso. Si ya hay un respaldo en estado 'En Progreso', el botón "Crear Respaldo Ahora" está deshabilitado (MatDisabled). No se permiten dos respaldos simultáneos. - E4: pg_dump error. Si pg_dump falla (BD en uso, permisos insuficientes, path no encontrado), "Respaldo fallido. No se pudo generar el volcado de la base de datos." - E5: Restauración. Si se presiona "Restaurar", se muestra confirmación: "¿Restaurar la base de datos desde este respaldo? Se sobrescribirán todos los datos actuales." Restauración solo vía flujo separado con supervisión. - E6: Sin permisos. Módulo no visible.
CASOS DE USO RELACIONADOS | CU01–CU26 (todas las operaciones que generan datos que deben respaldarse).
