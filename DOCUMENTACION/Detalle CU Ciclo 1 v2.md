## CU01 — Iniciar Sesión en Plataforma

CASO DE USO | CU01 - Iniciar Sesión en Plataforma
--- | ---
PROPÓSITO | Permitir a los usuarios autenticarse con credenciales válidas y acceder a la funcionalidad correspondiente a su rol en la plataforma web (Angular) o móvil (Flutter/Dart), estableciendo una sesión segura mediante JWT y registrando cada intento en la bitácora de auditoría.
DESCRIPCIÓN | La plataforma presenta una pantalla de inicio de sesión accesible desde la ruta /login (web Angular) o la pantalla LoginScreen (móvil Flutter). El formulario contiene dos campos de entrada — correo electrónico (type email, validación de formato) y contraseña (type password, con botón "mostrar/ocultar") — un botón principal "Iniciar Sesión", un enlace secundario "¿Olvidaste tu contraseña?" que redirige al flujo CU05, y un enlace "¿No tienes cuenta? Crear cuenta" que redirige a CU03. Al enviar el formulario, el componente LoginComponent (web) o LoginScreen (móvil) ejecuta una petición HTTP POST al endpoint /api/v1/auth/login del backend FastAPI con el body JSON { "email": string, "password": string }. El endpoint auth.login ejecuta la siguiente lógica: (a) busca el registro en la tabla usuarios WHERE email = :email y estado = 'Activo'; si no existe o estado ≠ 'Activo', retorna HTTP 401 con { "detail": "Correo o contraseña incorrectos" }; (b) verifica que usuarios.intentos_fallidos < 5; si es ≥ 5, calcula los minutos restantes del bloqueo (15 min desde usuarios.fecha_bloqueo) y retorna HTTP 429 con { "detail": "Demasiados intentos fallidos. Intenta de nuevo en X minutos." }; (c) compara el hash bcrypt de password con usuarios.password_hash usando bcrypt.verify(); si no coincide, incrementa usuarios.intentos_fallidos += 1, si al incrementar alcanza 5, registra usuarios.fecha_bloqueo = NOW() y usuarios.intentos_fallidos = 5, retorna HTTP 401; (d) si coincide, resetea usuarios.intentos_fallidos = 0, genera un JWT con payload { "sub": usuarios.id, "email": usuarios.email, "rol": usuarios.rol, "permisos": roles.permisos_json } usando HS256 con expiración de 8 horas (access_token) y 7 días (refresh_token); (e) inserta en bitacora_auditoria: { accion_sql: 'LOGIN', tabla_afectada: 'usuarios', registro_id: usuarios.id, ip_address: request.client.host, user_agent: request.headers['user-agent'], new_data: { resultado: 'Exitoso' } }; (f) retorna HTTP 200 con { "access_token": string, "refresh_token": string, "token_type": "bearer", "user": { "id": int, "email": string, "nombre": string, "rol": string, "avatar": string } }. En el cliente web (Angular), el AuthService almacena access_token en una httpOnly cookie名叫 'session_tt' con path '/' y SameSite=Lax, y refresh_token en sessionStorage. El AuthGuard en app-routing.module.ts evalúa el rol del usuario y redirige: rol='Administrador' → /inicio, rol='Encargado' → /sucursal, rol='Cajero' → /caja, rol='Cliente' → /catalogo. En el cliente móvil (Flutter), se almacena en flutter_secure_storage. Se permite un máximo de 5 intentos fallidos consecutivos; al alcanzar 5, la cuenta se bloquea temporalmente por 15 minutos (usuarios.fecha_bloqueo = NOW(), se verifica con DATEDIFF(NOW(), fecha_bloqueo) < 15 minutos en cada intento subsiguiente).
ACTORES | Administrador General, Encargado de Sucursal, Cajero, Cliente.
ACTOR INICIADOR | Cualquier usuario que desee acceder a la plataforma Tiendas Montaño.
PRECONDICIÓN | - El usuario debe existir en la tabla usuarios (usuarios.id, usuarios.email, usuarios.password_hash, usuarios.estado, usuarios.rol, usuarios.intentos_fallidos) con estado = 'Activo'. - Si el usuario es un empleado nuevo registrado por CU07, debe haber completado CU06 (Establecer Primera Contraseña) previamente, lo que cambia usuarios.estado de 'Pendiente' a 'Activo'. - La tabla roles debe contener el registro correspondiente al rol del usuario (roles.id, roles.nombre_rol, roles.permisos_json). - Para empleados, la tabla usuarios_empleados debe tener el registro vinculando usuarios.id con usuarios_empleados.sucursal_id y usuarios_empleados.rol.
FLUJO PRINCIPAL (Camino Feliz) | 1. El usuario abre la aplicación web (navegador → tiendasmontano.com) o la aplicación móvil. 2. Si no hay sesión activa, el sistema redirige a /login (web) o muestra LoginScreen (móvil). 3. El formulario carga con campos vacíos y validación deshabilitada. 4. El usuario ingresa su correo electrónico en el campo email. El componente ejecuta validación en tiempo real: expresión regular /^[^\s@]+@[^\s@]+\.[^\s@]+$/ — si no coincide, muestra borde rojo y mensaje "Ingresa un correo válido" debajo del campo. 5. El usuario ingresa su contraseña en el campo password. 6. El usuario presiona "Iniciar Sesión". 7. El LoginComponent envía POST /api/v1/auth/login con body { email, password }. 8. El backend busca usuarios WHERE email = :email. Si no existe → E1. Si estado = 'Inactivo' → E2. 9. Verifica usuarios.intentos_fallidos < 5. Si ≥ 5 → E3. 10. Verifica bcrypt.verify(password, usuarios.password_hash). Si falla → incrementa intentos_fallidos, si alcanza 5 bloquea 15 min, retorna E1. 11. Si coincide: resetea intentos_fallidos = 0, genera JWT (access + refresh), inserta en bitacora_auditoria, retorna HTTP 200 con tokens y datos de usuario. 12. El frontend almacena access_token en httpOnly cookie (web) o SecureStorage (móvil). 13. El AuthGuard redirige según usuarios.rol al panel correspondiente. 14. El sistema muestra un toast "Bienvenido/a, [nombre]" en la esquina superior derecha.
POST CONDICIÓN | El usuario tiene una sesión activa con JWT válido (expira en 8 horas), puede navegar por las funcionalidades autorizadas según roles.permisos_json, y el evento queda registrado en bitacora_auditoria con IP, dispositivo y timestamp. La tabla usuarios se actualiza: intentos_fallidos = 0, fecha_ultimo_acceso = NOW().
EXCEPCIONES (Flujo Secundario) | - E1: Credenciales inválidas. Si usuarios.email no existe en la tabla o usuarios.password_hash no coincide con bcrypt.verify(), el sistema retorna HTTP 401 con { "detail": "Correo o contraseña incorrectos" }. El frontend muestra un toast de error (color rojo, duración 5s) con el mensaje exacto. Se incrementa usuarios.intentos_fallidos en +1. Se inserta en bitacora_auditoria: { accion_sql: 'LOGIN_FAILED', tabla_afectada: 'usuarios', registro_id: NULL, new_data: { email_intentado: email, razon: 'Credenciales inválidas' } }. No se revela si el email existe o no (previene enumeración de usuarios). - E2: Cuenta deshabilitada. Si usuarios.estado = 'Inactivo', el backend retorna HTTP 403 con { "detail": "Tu cuenta está deshabilitada. Contacta al administrador de Tiendas Montaño." }. El frontend muestra un toast con el mensaje exacto y un botón "Contactar soporte" que abre mailto:soporte@tiendasmontano.com. No se valida la contraseña (seguridad). Se registra en bitacora_auditoria. - E3: Cuenta bloqueada por intentos. Si usuarios.intentos_fallidos >= 5, el backend calcula minutos_restantes = 15 - DATEDIFF(MINUTE, usuarios.fecha_bloqueo, NOW()). Si minutos_restantes > 0, retorna HTTP 429 con { "detail": "Demasiados intentos fallidos. Tu cuenta está bloqueada temporalmente. Intenta de nuevo en X minutos." }. El frontend deshabilita el botón "Iniciar Sesión" y muestra un countdown en tiempo real ("Disponible en 14:32 min"). Si minutos_restantes <= 0, resetea intentos_fallidos = 0 y permite el intento. - E4: Token JWT expirado (sesión previa). Si el usuario ya tenía un JWT almacenado pero expiró, el AuthGuard detecta HTTP 401 en el primer request al backend, limpia storage y redirige a /login con el toast "Tu sesión ha expirado. Inicia sesión nuevamente." - E5: Error de red/servidor. Si el backend no responde (timeout > 10s o HTTP 500), el frontend muestra "Error de conexión. Verifica tu acceso a internet e intenta de nuevo." con botón "Reintentar".
CASOS DE USO RELACIONADOS | CU02 (Cerrar Sesión), CU03 (Registrar Cliente), CU05 (Recuperar Contraseña), CU06 (Establecer Primera Contraseña), CU07 (Registrar Empleado).

## CU02 — Cerrar Sesión Activa

CASO DE USO | CU02 - Cerrar Sesión Activa
--- | ---
PROPÓSITO | Permitir al usuario cerrar su sesión de forma segura, invalidando el token JWT activo, eliminando las credenciales almacenadas en el dispositivo y registrando el evento en la bitácora de auditoría para garantizar la trazabilidad del cierre.
DESCRIPCIÓN | El usuario presiona el botón "Cerrar Sesión" ubicado en el menú de perfil. En la web Angular, este botón se encuentra en el componente HeaderComponent dentro del dropdown del avatar (barra superior derecha), visible tras hacer clic en el avatar del usuario. En la app móvil Flutter, el botón "Cerrar Sesión" se encuentra en el Drawer del menú hamburguesa o en la pantalla de Perfil. Al presionarlo, el frontend muestra un MatDialog (web) o showDialog (móvil) con el mensaje "¿Estás seguro que deseas cerrar tu sesión? Se cerrará la sesión en todos los dispositivos." y dos botones: "Cerrar Sesión" (primario, rojo) y "Cancelar" (secundario). Si el usuario confirma, el frontend ejecuta: (a) petición HTTP POST /api/v1/auth/logout con header Authorization: Bearer {access_token}; (b) el backend auth.logout agrega el jti (JWT ID) del token a la tabla token_blacklist con campos: jti (UUID), token_type = 'access', expires_at (timestamp de expiración original del JWT), usuario_id, created_at = NOW(); (c) el backend inserta en bitacora_auditoria: { accion_sql: 'LOGOUT', tabla_afectada: 'usuarios', registro_id: usuario.id, ip_address, user_agent, new_data: { duracion_sesion: minutos_desde_login } }; (d) retorna HTTP 200 con { "detail": "Sesión cerrada exitosamente" }. (e) El frontend elimina la cookie httpOnly 'session_tt' (web) o SecureStorage.clear() (móvil). (f) El frontend redirige a /login con un toast "Sesión cerrada correctamente."
ACTORES | Todos los usuarios autenticados (Administrador General, Encargado de Sucursal, Cajero, Cliente).
ACTOR INICIADOR | El usuario que desea cerrar su sesión activa de forma intencional.
PRECONDICIÓN | - El usuario debe tener una sesión activa: JWT válido (no expirado) almacenado en httpOnly cookie (web) o SecureStorage (móvil). - El token JWT debe contener los campos sub, email, rol y jti en su payload. - La tabla token_blacklist debe existir en la base de datos (schema público) con las columnas: id (serial PK), jti (UUID UNIQUE), token_type (varchar), expires_at (timestamp), usuario_id (FK → usuarios.id), created_at (timestamp).
FLUJO PRINCIPAL (Camino Feliz) | 1. El usuario presiona su avatar en la barra superior (web) o abre el menú hamburguesa (móvil). 2. El dropdown/drawer muestra las opciones: "Mi Perfil", "Configuración", "Cerrar Sesión". 3. El usuario presiona "Cerrar Sesión". 4. El frontend muestra el diálogo de confirmación: "¿Estás seguro que deseas cerrar tu sesión?" 5. El usuario presiona "Cerrar Sesión" (botón rojo) en el diálogo. 6. El frontend envía POST /api/v1/auth/logout con header Authorization: Bearer {access_token}. 7. El backend extrae el jti del payload del JWT (sin verificar expiración — permite cerrar aunque el token esté por expirar). 8. El backend inserta en token_blacklist: { jti: payload.jti, token_type: 'access', expires_at: payload.exp, usuario_id: payload.sub, created_at: NOW() }. 9. El backend inserta en bitacora_auditoria: { accion_sql: 'LOGOUT', tabla_afectada: 'usuarios', registro_id: payload.sub, new_data: { duracion_sesion: "X minutos" } }. 10. Retorna HTTP 200. 11. El frontend elimina la cookie 'session_tt' con max-age=0 (web) o ejecuta SecureStorage.delete(key: 'access_token') + SecureStorage.delete(key: 'refresh_token') (móvil). 12. Redirige a /login con toast "Sesión cerrada correctamente."
POST CONDICIÓN | La sesión queda permanentemente invalidada: el token JWT ya no puede ser utilizado para acceder a ningún endpoint del backend (el middleware de autenticación FastAPI verifica token_blacklist antes de validar el JWT). El usuario es redirigido a /login. El evento queda registrado en bitacora_auditoria.
EXCEPCIONES (Flujo Secundario) | - E1: JWT ya expirado. Si el JWT del usuario ya expiró cuando presiona "Cerrar Sesión", el frontend detecta el error HTTP 401 en la petición POST /logout, pero de todas formas elimina las credenciales del cliente y redirige a /login sin mostrar error. No se registra en token_blacklist (el token ya expiró naturalmente). Se muestra toast "Sesión cerrada." - E2: Error de red. Si la petición POST /logout falla por timeout o error de red, el frontend igualmente elimina las credenciales locales (cookie o SecureStorage) y redirige a /login. Se muestra toast "Sesión cerrada localmente." La invalidación remota del token se producirá cuando el backend detecte su expiración natural o cuando el AuthGuard lo rechace en el próximo request. - E3: Token en token_blacklist ya existente. Si el jti ya existe en token_blacklist (doble cierre), el backend retorna HTTP 200 igualmente (idempotente) y el frontend procede normalmente.
CASOS DE USO RELACIONADOS | CU01 (Iniciar Sesión).

## CU03 — Registrar Nuevo Cliente

CASO DE USO | CU03 - Registrar Nuevo Cliente
--- | ---
PROPÓSITO | Permitir a un usuario nuevo crear una cuenta de cliente en la plataforma Tiendas Montaño para poder consultar el catálogo, reservar prendas para probarlas en tienda, comprar en línea, utilizar el vestidor virtual con realidad aumentada y recibir recomendaciones personalizadas de IA.
DESCRIPCIÓN | Desde la pantalla de login, el usuario presiona el enlace "¿No tienes cuenta? Crear cuenta" que redirige a la ruta /registro (web Angular) o a la pantalla RegisterScreen (móvil Flutter). El formulario contiene los siguientes campos: nombre completo (texto, requerido, mín. 2 caracteres), correo electrónico (email, requerido, formato válido, único en tabla usuarios), contraseña (password, requerido, mín. 8 caracteres, al menos 1 mayúscula, 1 minúscula, 1 número y 1 carácter especial [!@#$%^&*]), confirmar contraseña (password, requerido, debe coincidir con contraseña), teléfono (teléfono, opcional, formato boliviano +591 XXXXXXX), y checkbox "Acepto los Términos y Condiciones" (obligatorio). La validación es en tiempo reactiva (Angular: ReactiveFormsModule con validators; Flutter: TextFormField con validator). Cada campo muestra su estado de validación en vivo: borde verde si es válido, borde rojo + mensaje de error si no cumple. El botón "Crear Cuenta" se deshabilita (opacity-50, pointer-events-none) hasta que todos los campos obligatorios sean válidos y el checkbox esté marcado. Al presionar "Crear Cuenta", el frontend envía POST /api/v1/clientes/registrar con body { "nombre": string, "email": string, "password": string, "telefono": string|null }. El endpoint clientes.registrar ejecuta: (a) valida que usuarios.email no exista previamente en la tabla usuarios (SELECT COUNT(*) FROM usuarios WHERE email = :email); si existe, retorna HTTP 409 con { "detail": "Ya existe una cuenta con este correo electrónico." }; (b) hashea la contraseña con bcrypt.hash(password, rounds=12); (c) inserta en usuarios: { email, password_hash, nombre, rol: 'Cliente', estado: 'Activo', intentos_fallidos: 0, fecha_creacion: NOW(), fecha_ultimo_acceso: NULL }; (d) captura usuarios.id retornado; (e) inserta en clientes: { usuario_id: usuarios.id, nombre, email, telefono, fecha_registro: NOW(), preferencias_json: "{}" }; (f) genera un token de confirmación UUID y lo inserta en email_confirmations: { usuario_id, token, expires_at: NOW() + 24 horas, used: false }; (g) envía un email transaccional de bienvenida al correo del cliente con asunto "Bienvenido a Tiendas Montaño — Confirma tu cuenta" y un enlace de confirmación /confirmar-cuenta?token=xxx; (h) inserta en bitacora_auditoria: { accion_sql: 'INSERT', tabla_afectada: 'clientes', registro_id: cliente.id, new_data: { nombre, email } }; (i) retorna HTTP 201 con { "detail": "Cuenta creada exitosamente. Revisa tu correo para confirmar tu cuenta.", "cliente_id": int }. El frontend muestra un toast de éxito y redirige a /login con el mensaje "Cuenta creada. Ya puedes iniciar sesión." La confirmación de email (abrir enlace) es opcional para el MVP; el usuario puede iniciar sesión sin confirmar.
ACTORES | Cliente (usuario nuevo, sin cuenta previa).
ACTOR INICIADOR | Persona que desea crear una cuenta de cliente en Tiendas Montaño, ya sea por primera vez o tras conocer la plataforma.
PRECONDICIÓN | - No debe existir un registro en la tabla usuarios con el mismo email (usuarios.email UNIQUE constraint). - La tabla usuarios debe tener la columna estado con valores permitidos: 'Activo', 'Inactivo', 'Pendiente'. Para clientes, se asigna directamente 'Activo' (a diferencia de empleados que inician como 'Pendiente' — CU07). - La tabla clientes debe existir con las columnas: id (serial PK), usuario_id (FK → usuarios.id), nombre, email, telefono, fecha_registro, preferencias_json (JSONB para guardar preferencias de la IA). - La tabla email_confirmations debe existir para el flujo de confirmación de email.
FLUJO PRINCIPAL (Camino Feliz) | 1. El usuario presiona "Crear cuenta" en /login. 2. El sistema muestra el formulario de registro vacío con todos los campos deshabilitados de validación (sin errores visuales). 3. El usuario ingresa "María López" en nombre completo. Validación: minLength=2 ✓ → borde verde. 4. Ingresa "maria@correo.com" en email. Validación: formato email ✓, consulta única async al backend (debounce 500ms) para verificar unicidad → "Disponible" ✓. 5. Ingresa "MiClave#2026" en contraseña. Validación regex ✓ (8+ chars, mayúscula, minúscula, número, especial) → indicador de fortaleza: "Fuerte" (barra verde). 6. Ingresa "MiClave#2026" en confirmar contraseña → coincide ✓. 7. Ingresa "+59171234567" en teléfono (opcional). 8. Marca "Acepto los Términos y Condiciones". 9. El botón "Crear Cuenta" se habilita (opacity-100, pointer-events-auto). 10. Presiona "Crear Cuenta". 11. Frontend envía POST /api/v1/clientes/registrar con body { nombre, email, password, telefono }. 12. Backend verifica unicidad de email en usuarios. OK. 13. Backend crea hash bcrypt de password. 14. Backend INSERT en usuarios: { email, password_hash, nombre, rol: 'Cliente', estado: 'Activo', fecha_creacion: NOW() }. 15. Backend INSERT en clientes: { usuario_id, nombre, email, telefono, fecha_registro: NOW(), preferencias_json: "{}" }. 16. Backend INSERT en email_confirmations: { usuario_id, token: UUID, expires_at: NOW()+24h, used: false }. 17. Backend envía email de bienvenida (servicio de correo transaccional). 18. Backend INSERT en bitacora_auditoria: { accion_sql: 'INSERT', tabla_afectada: 'clientes', new_data: { nombre, email } }. 19. Retorna HTTP 201. 20. Frontend muestra toast "Cuenta creada exitosamente." y redirige a /login. 21. El usuario inicia sesión (CU01) y es redirigido a /catalogo (rol Cliente).
POST CONDICIÓN | Existe un registro activo en la tabla usuarios (rol='Cliente', estado='Activo') y un registro vinculado en la tabla clientes. El usuario puede iniciar sesión (CU01), acceder al catálogo (CU16), hacer reservas (CU28), comprar (CU34, CU35) y usar el vestidor virtual (CU32). Las preferencias del cliente se inicializan vacías en clientes.preferencias_json y se irán poblando con las interacciones de compra y navegación para alimentar las recomendaciones de IA (CU41).
EXCEPCIONES (Flujo Secundario) | - E1: Email ya registrado. Si POST /api/v1/clientes/recibe un email que ya existe en usuarios.email, el backend retorna HTTP 409 con { "detail": "Ya existe una cuenta con este correo electrónico." }. El frontend muestra un toast de error y coloca foco en el campo email con borde rojo y el mensaje "Este correo ya está registrado" debajo. No se revela si la cuenta está activa o inactiva (seguridad). Se registra en bitacora_auditoria: { accion_sql: 'REGISTER_FAILED', new_data: { email, razon: 'Email duplicado' } }. - E2: Contraseña débil. Si la contraseña no cumple la regex (mín. 8 chars, 1 mayúscula, 1 minúscula, 1 número, 1 especial), el frontend muestra debajo del campo: "La contraseña debe tener al menos 8 caracteres, una mayúscula, una minúscula, un número y un carácter especial (!@#$%^&*)." El botón "Crear Cuenta" permanece deshabilitado. - E3: Contraseñas no coinciden. Si confirmar_contraseña ≠ contraseña, el frontend muestra "Las contraseñas no coinciden" debajo del campo con borde rojo. Botón deshabilitado. - E4: Nombre muy corto. Si nombre tiene menos de 2 caracteres: "El nombre debe tener al menos 2 caracteres." - E5: Email en formato inválido. Si el campo email no pasa la validación regex de formato: "Ingresa un correo electrónico válido." - E6: Términos no aceptados. Si el checkbox no está marcado, el botón "Crear Cuenta" permanece deshabilitado. - E7: Error de servidor (HTTP 500). "Error al crear la cuenta. Intenta de nuevo en unos momentos." Botón "Reintentar" disponible. - E8: Error de envío de email. Si el email de bienvenida no se pudo enviar (servicio de correo caído), el cliente se registra igualmente pero el sistema muestra una alerta al Administrador en el dashboard: "No se pudo enviar el email de bienvenida a [email]. Reenvía manualmente."
CASOS DE USO RELACIONADOS | CU01 (Iniciar Sesión), CU05 (Recuperar Contraseña — si olvidó la contraseña después del registro).

## CU04 — Cambiar Contraseña Propia

CASO DE USO | CU04 - Cambiar Contraseña Propia
--- | ---
PROPÓSITO | Permitir al usuario autenticado actualizar su contraseña de acceso desde su perfil de usuario, como medida de seguridad preventiva o reactiva, garantizando que la contraseña actual sea verificada antes del cambio y que el evento quede registrado en la bitácora de auditoría.
DESCRIPCIÓN | Desde la pantalla "Mi Perfil" (ruta /mi-perfil en web Angular, pantalla ProfileScreen en Flutter móvil), el usuario accede a la sección "Seguridad" (tab o sección expandible). Esta sección contiene un botón "Cambiar Contraseña" que abre un modal/dialog con tres campos: contraseña actual (password, requerido), nueva contraseña (password, requerido, mismas reglas que CU03: mín. 8 chars, mayúscula, minúscula, número, especial), y confirmar nueva contraseña (password, requerido, debe coincidir). El formulario aplica validación en tiempo real igual a CU03. La nueva contraseña debe ser diferente de la actual (validación backend). Al enviar, el frontend envía PUT /api/v1/auth/cambiar-contraseña con header Authorization: Bearer {access_token} y body { "password_actual": string, "password_nueva": string }. El endpoint auth.cambiar-contraseña ejecuta: (a) verifica que el JWT sea válido y extrae usuarios.id del payload; (b) consulta usuarios WHERE id = :id; (c) verifica bcrypt.verify(password_actual, usuarios.password_hash); si falla, retorna HTTP 401 { "detail": "La contraseña actual es incorrecta." }; (d) verifica que password_nueva ≠ password_actual (comparación de strings, no de hashes); si son iguales, retorna HTTP 400 { "detail": "La nueva contraseña debe ser diferente a la actual." }; (e) hashea password_nueva con bcrypt.hash(password_nueva, 12); (f) UPDATE usuarios SET password_hash = :nuevo_hash, fecha_actualizacion = NOW() WHERE id = :id; (g) INSERT en bitacora_auditoria: { accion_sql: 'UPDATE', tabla_afectada: 'usuarios', registro_id: id, new_data: { accion: 'Cambio de contraseña', ip_address: request.client.host } }; (h) retorna HTTP 200 { "detail": "Contraseña actualizada correctamente." }. El frontend muestra toast de éxito y cierra el modal.
ACTORES | Administrador General, Encargado de Sucursal, Cajero, Cliente (cualquier usuario autenticado).
ACTOR INICIADOR | El usuario que desea cambiar su contraseña de acceso por decisión propia o como respuesta a una alerta de seguridad.

## CU05 — Recuperar Contraseña Olvidada

--- | ---
PROPÓSITO | Permitir al usuario restablecer su contraseña cuando la ha olvidado o fue comprometida, mediante un enlace de un solo uso enviado a su correo electrónico registrado, garantizando que solo el propietario legítimo de la cuenta pueda establecer una nueva contraseña.

Envía un email transaccional con asunto "Tiendas Montaño — Restablece tu contraseña" y un enlace https://tiendasmontano.com/restablecer-contraseña?token=xxx. Al abrir el enlace, el usuario ve un formulario con: nueva contraseña y confirmar contraseña. Al enviar, el backend valida el token (existe, no expirado, used=false), actualiza password_hash y marca used=true.
ACTORES | Cliente, Administrador General, Encargado de Sucursal, Cajero (cualquier usuario con cuenta activa).
ACTOR INICIADOR | El usuario que ha olvidado su contraseña y necesita restablecerla.
PRECONDICIÓN | - El usuario debe tener una cuenta activa en la tabla usuarios con estado = 'Activo' y un email válido registrado. - La tabla password_resets debe existir con las columnas: id, usuario_id, token, expires_at, used, created_at. - Debe haber un servicio de correo transaccional configurado en el backend (SMTP o API de envío de emails).
FLUJO PRINCIPAL (Camino Feliz) | 1. El usuario presiona "¿Olvidaste tu contraseña?" en /login. 2. El sistema muestra /recuperar-contraseña con campo email. 3. Ingresa "maria@correo.com". 4. Si existe: genera token = uuid_v4(), INSERT en password_resets: { usuario_id, token, expires_at: NOW()+30min, used: false, created_at: NOW() }. 8. Backend envía email con enlace /restablecer-contraseña?token={token}. 9. Backend retorna HTTP 200 { "detail": "Si el correo está registrado, recibirás un enlace para restablecer tu contraseña." } (siempre, sin importar si el email existe). 10. Frontend muestra toast "Revisa tu correo electrónico. Te enviamos un enlace para restablecer tu contraseña." y redirige a /login. 11. El usuario abre su correo, presiona el enlace → redirige a /restablecer-contraseña?token=xxx. 12. El frontend valida que el token esté presente en la URL. 13. Muestra formulario: nueva contraseña + confirmar contraseña. 14. El usuario ingresa "NuevaClave#2026" y la confirma. 15. Frontend envía PUT /api/v1/auth/reset-password con { token: "xxx", password: "NuevaClave#2026" }. 16. Backend busca password_resets WHERE token = :token. Si no existe → E2. Verifica used = false. Si used = true → E3. Verifica expires_at > NOW(). Si expirado → E2. 17. Backend hashea la nueva contraseña con bcrypt.hash(password, 12). 18. Backend UPDATE usuarios SET password_hash = :hash, fecha_actualizacion = NOW() WHERE id = password_resets.usuario_id. 19. Backend UPDATE password_resets SET used = true WHERE token = :token. 20. Backend INSERT en bitacora_auditoria: { accion_sql: 'RESET_PASSWORD', tabla_afectada: 'usuarios', registro_id: usuario_id, new_data: { metodo: 'email_reset' } }. 21. Retorna HTTP 200 { "detail": "Contraseña restablecida exitosamente." }. 22. Frontend muestra "Contraseña restablecida. Ya puedes iniciar sesión." y redirige a /login.

EXCEPCIONES (Flujo Secundario) | - E1: Email no registrado (seguridad). Solicita uno nuevo si necesitas cambiar tu contraseña nuevamente." } con botón "Solicitar nuevo enlace". - E4: Token inexistente. El frontend valida antes de enviar la petición (mismas reglas que CU03). No llega al backend. - E6: Contraseñas no coinciden. "Las contraseñas no coinciden." Validación de frontend. - E7: Enlace con token de más de 8 caracteres eliminados en URL.
