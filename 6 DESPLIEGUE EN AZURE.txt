DESPLIEGUE EN AZURE, PASO A PASO
Plataforma Web y Movil de E-Commerce - Tiendas Montano

Este documento es una lista de pasos. Se hacen en orden y no hace falta decidir nada
por el camino. Al final hay una lista de comprobacion.

Lo que se despliega

  Backend      NestJS, 71 rutas      ->  Azure App Service para Linux
  Frontend     React 19, 35 pantallas ->  Azure Static Web Apps
  Base de datos  ya esta en Supabase   ->  no se hace nada, no se toca

El backend y el frontend van en el MISMO dominio, con el Static Web Apps haciendo de
proxy hacia el App Service. Asi no hay CORS, no hay problema de cookies y el codigo no
se toca, porque el cliente HTTP del frontend ya pide rutas relativas: en
web/src/lib/api.ts, linea 1015, tiene puesto baseUrl: '/api/v1'.

Costo: 0. App Service tiene plan Free, Static Web Apps tiene plan Free.

FASE 1. CREAR EL RECURSO COMPARTIDO DE ARCHIVOS
=====================================================================

Esto es lo que mas se olvida y lo que hace que se pierdan las facturas. Se hace primero
porque despues hay que montarlo en el App Service.

Por que. En Azure App Service el disco del sistema se borra en cada reinicio, en cada
despliegue y en cada escalado. Todo lo que el sistema escribe: los PDF de las facturas,
los respaldos de la base de datos y los reportes, se perderian. Un recurso compartido de
archivos es un disco que no se borra.

1.1  En https://portal.azure.com, menu de la izquierda, Storage accounts.
     Si no aparece, busca "Storage accounts" en el buscador de arriba.

1.2  Create. Los datos:

       Subscription          la que tengas
       Resource group         Create new, y ponle: tiendas-montano
       Storage account name   tmplazemontano
       Region                la que te quede mas cerca. La de Supabase es sa-east-1,
                              en Sao Paulo, y es la que menos latencia da.
       Primary performance    Standard
       Redundancy            la que venga por defecto
       Access tier            Hot, o el que venga por defecto

1.3  Create, y espera un minuto.

1.4  En el almacen, menu Files > File shares > File share > Create.

       Nombre                 almacen
       Cuota                  5 GiB, que es lo minimo y sobra

1.5  Anota la URL del recurso compartido. Sale en Overview > Endpoint > File share
     endpoint, y tiene esta forma:

       https://tmplazemontano.file.core.windows.net/almacen

     La parte que te interesa es el nombre, tmplazemontano, que usaremos en la Fase 3.

1.6  No hace falta crear ningun contenedor de blobs. Eso es para cuando se implemente
     Azure Blob Storage, que es el arreglo definitivo y no el de ahora.

FASE 3. MONTAR EL DISCO Y PONER LAS VARIABLES DE ENTORNO
=====================================================================

3.1  Montar el recurso compartido. En el App Service, menu Configuration > Mount paths.

       Add, y rellena:

         Name               storage
         Share name         almacen
         Mount path         /home/storage
         Access rights      Read/Write

3.2  Añadir las variables de entorno. Menu Configuration > Environment variables > Add.
     Añade estas una por una:

       PORT                      8080
       DATABASE_URL              la cadena de Supabase con la clave nueva
       JWT_SECRET                una cadena larga y aleatoria, de 64 caracteres o mas
       JWT_ACCESS_TOKEN_MINUTES  15
       JWT_REFRESH_TOKEN_DAYS    7
       JWT_ALGORITHM             HS256
       COOKIE_SECURE             true
       CORS_ORIGINS              la direccion del Static Web Apps, sin https y sin barra
       EMAIL_ENABLED             false
       STORAGE_BACKEND           local
       STORAGE_COMPROBANTES      /home/storage/comprobantes
       RESPALDOS_DIR             /home/storage/respaldos
       STORAGE_PATH              /home/storage/reportes

     CUATRO DE ESTAS NECESITAS EXPLICACION:

     PORT tiene que ser 8080. Azure App Service para Linux espera que la aplicacion
     escuche en ese puerto, y lo lee de la variable PORT. El codigo, en main.ts linea 45,
     hace config.get('PORT', 3000), o sea que si pones la variable, gana la variable.

     COOKIE_SECURE tiene que ser true. En tu .env local vale false porque trabajas en
     http. En Azure todo va por https, y si esto se queda en false el navegador no
     guarda las cookies de sesion y el login va a parecer roto sin que haya ningun error.

     CORS_ORIGINS se escribe SIN https y SIN barra final. Por ejemplo, si el Static Web
     Apps acaba en https://tm-web-123.azurestaticapps.net, aqui va:
         tm-web-123.azurestaticapps.net
     Si son varios, separados por comas y sin espacios.

     STORAGE_COMPROBANTES es la variable nueva. Antes el codigo tenia escrito
     process.env.STORAGE_BACKEND === 's3' ? 'comprobantes' : 'comprobantes', o sea que
     las dos ramas eran iguales y no hacia nada. Ahora lee directamente de aqui, y por eso
     los PDF van al disco que no se borra.

     NO ANADAS RESPALDOS_PG_DUMP_PATH. La que tienes apunta a
     C:\Users\pablo\AppData\Local\Temp\..., que es una ruta de Windows y no existe en
     Linux. Si la pones, el servicio de respaldos falla. Si no la pones, el codigo usa el
     nombre pg_dump a secas, que tampoco esta instalado. Los respaldos automaticos no
     van a funcionar en la nube hasta que se resuelva, y eso se documenta como pendiente.

3.3  Click Save. Te pide reiniciar, y le dices que si.

3.4  Sube el .env con la clave nueva. Copia la linea DATABASE_URL de tu archivo local
     PROTOTIPO/api/.env, que ya tiene la clave que cambiaste, y pegala como valor de
     DATABASE_URL. Lo mismo con JWT_SECRET: usa el de tu .env local para que las sesiones
     que ya tengas sigan valiendo.

FASE 4. LOS COMANDOS DE COMPILACION Y DE ARRANQUE
=====================================================================

4.1  En el App Service, menu Configuration > General settings, o el enlace Build de
     arriba. Rellena:

       Build command        cd api && npm ci --include=dev && npm run build
       Startup command      cd api && node dist/main
       App stack            Node 22 LTS
       Runtime version      22.x
       Always On            On, si esta disponible en tu plan

     POR QUE ESCRIBO cd api EN LOS DOS. El repositorio tiene tres carpetas: api, web y la
     raiz. El App Service solo necesita el backend. El comando de compilacion instala
     las dependencias incluidas las de desarrollo, porque nest build esta ahi y sin el no
     compila. El de arranque solo necesita las de produccion.

     Startup command NO es npm start. Ese es el modo de desarrollo, con recarga
     automatica y sin compilar. En produccion es node dist/main, que es lo que produce
     nest build.

4.2  Click Save.

4.3  En el menu Deployment > Deployment center, click Re-deploy. Empieza a instalar
     dependencias, que tarda tres o cuatro minutos la primera vez.

       https://api-tiendasmontano.azurewebsites.net/api/v1/carrito

FASE 8. LO QUE QUEDA PENDIENTE
=====================================================================

8.1  Los respaldos automaticos no funcionan en la nube. La causa es que el ejecutable
     pg_dump no esta instalado en la imagen de Node de Azure, y el que tienes apunta a
     una ruta de Windows. Hay dos salidas: instalar el cliente de PostgreSQL en un
     contenedor propio, o desactivar los respaldos automaticos y documentarlo. Para una
     demostracion yo desactivaria y lo dejaria escrito.

8.2  El almacenamiento en Azure Blob Storage no esta implementado. La variable
     STORAGE_BACKEND existe y se lee, pero en el servicio de comprobantes las dos ramas
     del ternario eran la misma palabra, y en el de respaldos el propio codigo avisa que
     el modo S3 no esta configurado. Con el recurso compartido de archivos de la Fase 1
     esto ya no es urgente, porque el disco persiste, pero si mañana quieres varias
     instancias a la vez, hay que pasarse a Blob Storage.

8.3  El webhook de la pasarela de pago queda apuntando a una pasarela simulada que esta
     dentro del propio servidor, en la ruta POST sandbox/gateway. En produccion hay que
     apuntar a una pasarela de verdad, y eso es un trabajo aparte.

8.4  La base de datos de produccion tiene 7 productos y 48 variantes, segun lo que se
     comprobó al desplegar. El archivo de datos de prueba siembra 24 productos y 78
     variantes. Si vas a enseñar el catalogo en la demostracion, hay que cargar los datos
     de prueba primero.

8.5  El motor de recomendaciones y el buscador del punto de venta filtran el estado de
     los productos por una palabra que no es la que trae el esquema, asi que devuelven
     cero resultados. Eso se arregla en el codigo, no en Azure.

9.1  Lo que SI se creo, y funciona:

      Grupo de recursos  tiendas-montano, en Brazil South
      Storage account    tmazmontano, con el recurso compartido almacen de 5 GiB
      Static Web Apps    tiendas-montano-web
      Dominio del frontend  https://zealous-mud-0749ef510.5.azurestaticapps.net
      ACR                crmontanotiendas.azurecr.io, con la imagen tmapi:v1

      El frontend esta desplegado y responde. Se midio: pagina principal
      HTTP 200 en 609 ms, y 879 KB servidos entre el HTML, el paquete de
      JavaScript de 770 KB, la hoja de estilos de 63 KB y las imagenes.
      El flujo de trabajo de GitHub Actions completo la compilacion de Vite
      y subio el resultado sin errores.

9.2  Lo que NO se pudo crear, y el motivo exacto.

      El App Service del backend no se pudo crear. Azure devuelve esto:

        ERROR: Operation cannot be completed without additional quota.
        Additional details - Location:
        Current Limit (F1 VMs): 0
        Current Usage: 0
        Amount required for this deployment (F1 VMs): 1

      Y lo mismo con el plan Basico, que si tiene precio:

        Current Limit (B1 VMs): 0

9.3  La causa raiz no es el plan, ni la region, ni el nombre del recurso.

      Es que la suscripcion no tiene metodo de pago registrado. En una
      cuenta de pago por uso normal, Azure no concede cupo de cómputo a
      ninguna region mientras no haya una forma de pago. Por eso:

        - El plan gratuito F1 da cupo 0, porque el beneficio de cuenta
          gratuita no esta en esta suscripcion.
        - El plan Basico B1 tambien da cupo 0, aunque se pague.
        - Los recursos que no cuestan dinero si se crean: por eso
          existen el almacenamiento y el Static Web Apps.

      El dato se confirmo en el portal: la pagina de Cuotas sale vacia,
      con el aviso de que el proveedor no esta registrado para la
      suscripcion, y en Facturacion no hay ningun metodo de pago dado de
      alta. El cargo acumulado hasta la fecha es 0.00.

9.4  Alternativa preparada: Azure Container Apps.

      Como F1 no es posible, se probo la via que si tiene cuota gratuita
      mensual, que es Container Apps en plan de consumo. Se avanzo hasta el
      ultimo paso:

        - Se registro el proveedor Microsoft.App.
        - Se creo el registro de contenedores crmontanotiendas.azurecr.io.
        - Se escribio el Dockerfile de la API, en PROTOTIPO/api/Dockerfile.
        - La imagen se compilo correctamente y se subio al registro.
        - La creacion del entorno de Container Apps quedo bloqueada por el
          mismo motivo del punto 9.3, que tambien necesita infraestructura
          de pago.

      El Dockerfile queda en el repositorio y sirve para cualquier
      despliegue por contenedor. Es de dos etapas: la primera instala
      python3, make y g++ porque bcrypt es un modulo nativo y hay que
      compilarlo, y la segunda se lleva solo node_modules ya limpio de
      herramientas de desarrollo, dist y package.json.

      Un detalle que aparecio al compilar: el comando npm ci falla, porque
      exige que package.json y package-lock.json coincidan al byte y en
      este proyecto no coinciden. La imagen usa npm install, que resuelve
      lo mismo sin esa exigencia.

9.5  Que habria que hacer para terminar el despliegue.

      Registrar un metodo de pago en la suscripcion, con un limite de gasto
      bajo, y repetir la Fase 2 y la Fase 3 de esta guia. Nada mas cambia:
      la imagen ya esta compilada y subida, y la variables de entorno ya
      estan identificadas. Con eso el backend queda en servicio en unos
      diez minutos.

      El coste real de la aplicacion seria de céntimos al mes, porque con
      min-replicas en 0 el contenedor se apaga cuando no hay trafico y solo
      cobra mientras corre. Al borrar el recurso se deja de facturar.

9.6  Advertencia tecnica que queda pendiente para cuando se publique.

      Las cookies de sesion de CTR_Auth se emiten con sameSite igual a lax
      y sin atributo domain. Eso solo funciona si el sitio que las pone y
      el que hace las peticiones son el mismo. Con el frontend en
      azurestaticapps.net y el backend en otro dominio, la sesion duraria
      quince minutos, que es la duracion del token de acceso, y despues
      cairia.

      La solucion es que el Static Web Apps proxy las rutas /api hacia el
      backend, de modo que todo ocurre en el mismo origen. El campo que lo
      configura, api_location, solo se puede fijar al crear el recurso, por
      lo que probablemente haya que volver a crear el Static Web Apps
      poniendo ahi la direccion real del backend y no una ruta de carpeta.
      Es el punto 6.2 de la Fase 6, y es el que mas conviene no dejar para
      el final.
